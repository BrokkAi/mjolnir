This walkthrough takes a fresh installation from its first launch to a running agent session. Start in the repository you want Mjolnir to recognize:

```sh
cd path/to/your/repository
mj
```

## 1. Open the dashboard

Two words come up on every screen:

- A **profile** is one coding-agent account: which agent (Claude Code, Codex,
  Kimi Code, Grok Build, or Muse Code) and the home directory that holds its
  sign-in.
- A **target** is where the session runs: this machine directly (`localhost`),
  a local container, an SSH host, or an EC2 instance.

When no workspace exists, Mjolnir creates one using the current directory's
name, then leaves the dashboard ready for an explicit session. On Linux and
macOS, when there is no configuration yet, `mj` adds a `codex` profile that uses
`~/.codex` and a `localhost` target. It does not check that Codex is installed,
and it does not start a session.

Press **Create**, `N`, or `prefix+c` to open the full creation wizard. Choose the
profile, target, project, resources, and attached directories before launch.
Launch progress and failures appear on the dashboard. When the new session is
ready, type a prompt and press `Enter`. Use **prefix+s Settings** to discover agent
accounts, add SSH or EC2 connections, and change runtime options.

`mj setup` is optional. It does the same discovery from the shell: it looks
for signed-in agents and local container runtimes, writes what it finds to
`config.toml`, runs `mj doctor`, and ends by telling you to run `mj`. You can
skip it and use Settings instead.

### If no coding agent is installed

Mjolnir runs an agent you already use; it does not include one. `mj setup`
then prints `No existing Codex, Claude Code, Kimi Code, or Grok Build homes
found.`, and the dashboard says `Mjolnir needs a little fuel.` To fix this:

1. Install one supported agent and sign in with it once, using that agent's
   own instructions. For example, Claude Code: `npm install -g
   @anthropic-ai/claude-code`, then run `claude`. Codex: `npm install -g
   @openai/codex`, then run `codex login`. Signing in creates the agent's home
   directory (`~/.claude`, `~/.codex`, `~/.kimi-code`, `~/.grok`, or
   `~/.config/muse`).
2. Open Settings (`prefix+s`), choose **Agent Profiles**, and press **Detect
   profiles**, or run `mj setup` again.

Codex and Claude Code sessions on this machine also need Node.js 22 or newer
and npm on `PATH`; Mjolnir installs its own pinned copy of the agent with them.

The dashboard keeps its session list, Conversation and Prompt regions, target
capacity, and profile quota visible together.

## 2. Resolve any missing prerequisites

If the first session reports a prerequisite failure, detach with `prefix+q`, then run:

```sh
mj doctor
```

For machine-readable output, use:

```sh
mj doctor --json
```

Fix errors until the relevant profiles and targets report ready. If a harness profile needs authentication, run:

```sh
mj login --profile <profile-id>
```

Claude Code profiles can use the long-lived setup-token flow:

```sh
mj login --profile <profile-id> --setup-token
```

The login command is profile-aware: it runs the correct harness authentication flow and stores credentials in that profile's home. See [profiles](/profiles/) for isolation and authentication details, or [troubleshooting](/troubleshooting/) if `doctor` still reports a failure.

## 3. Create a custom session (optional)

For another agent, project, or target, press **Create** or `prefix+c` from anywhere
on the dashboard. The full new-session wizard walks through:

1. A harness profile.
2. A target on which the session will run, including its resource size when that target is resizable.
3. A project bundle, or an absolute project directory for a bare target.
4. A final review, where supported targets can also receive attached directories.

When only one target is available and it has no size to set, such as
`localhost` on a host without Podman or Docker, the wizard chooses it and skips
step 2. The review still shows the target.

## 4. Send the first prompt

Type a message in the Prompt pane and press `Enter`. While the harness is working you can type another message and press `Enter` to queue it. Press `Esc` to cancel the active turn without stopping the session.

Useful controls for the first run:

| Key | Action |
| --- | --- |
| `Tab` / `Shift+Tab` | Move through Workspaces, Sessions, Prompt, Targets, and Quota |
| `Page Up` / `Page Down` | Scroll the transcript from any focus |
| `prefix+?` | Open contextual help |
| `prefix+:` | Open the searchable command palette |
| `prefix+c` | Open the full creation wizard |
| `prefix+s` | Edit configuration in Settings |
| `prefix+q` | Detach this terminal |

The prefix is `ctrl+b`, the same as tmux: press it, release it, then press the second key. Every key here, including the prefix, is editable in `config.toml` under `[keys]`; see [Terminal surface](/terminal-surface/#prefix-key) for the full default table and [Configuration](/configuration/#keys-keys) for the syntax.

The [terminal surface guide](/terminal-surface/) covers pane sizing, the full composer keymap, the command palette, and `!` shell commands.

## 5. Detach and reconnect

Press `prefix+q` when you are ready to leave the terminal. Detaching closes only this dashboard: the daemon and sessions keep running, active turns continue, and queued prompts remain queued.

Reconnect with:

```sh
mj
```

Mjolnir reopens the session in your opened workspace whose agent spoke most recently and places the cursor in its Prompt pane. Other workspaces' sessions remain live and are available by selecting their workspace tab. To reach the same sessions from a browser, print the viewer address and access code with:

```sh
mj daemon status
```

See the [web viewer](/web-viewer/) for browser and phone access. For workspace selection, scripting, daemon operations, and every command-line flag, use the [CLI reference](/cli-reference/).

## What a session does to your repository

On the `localhost` target, a new session gets its own Git clone at
`.mj/clones/<id>` inside your repository. The clone starts on the default
branch of your `origin` remote (on your current branch when there is no
remote, or on the branch you name with `mj new --branch`), and its `origin` is
the same remote as yours. Your checkout is not changed: its branch, its files,
and any uncommitted changes stay as they are, and Mjolnir adds no branch to
your repository. To let the agent edit your checkout directly instead, clear
**Create isolated checkout** on the wizard's review step. Container, SSH, and
EC2 targets also work in their own clone and do not touch your checkout.

To get the work out:

- Print the diff: `mj diff --session <id>`.
- Write a patch file: `mj export --session <id> --kind patch --out work.patch`.
- Push it as a branch: `mj export --session <id> --kind branch --branch <name>`
  pushes the session's work to `origin` as `<name>`.
- Look at the clone itself: `git -C .mj/clones/<id> log`. Its commits are not
  in your repository until they are pushed.
- In the dashboard, `prefix+d` lists the changed files.

**Destroy session…** removes the clone and its recovery copy. Work that was not
pushed or exported is lost.

## What it costs

Mjolnir itself is free. Every agent turn, every automatic review, and every
automatic continuation turn uses your agent subscription's quota, the same as
if you ran the agent yourself. The Quota pane shows what is left. EC2 targets
start instances in your AWS account, and AWS bills you for them until the
session is suspended or destroyed. Nothing else is billed.

By default Mjolnir sends recent prompt and reply text to TypeSafe's Jev classifier through a public proxy. [Security boundaries](/security/#what-leaves-this-machine-by-default) lists everything that leaves your machine.

## Bring in a session from another tool (optional)

The Import tab of the session dialog (`prefix+g`) and `mj import` adopt a
session you started directly in Claude Code, Codex, Kimi Code, Grok Build, or
Muse Code. Import only reads your repository: it archives the tracked changes
into Mjolnir's data directory and does not change the checkout. When the
imported session has a single Git root, resuming it runs the agent in that live
checkout, not in a new clone. See [sessions](/sessions/#import-a-native-harness-session).

## Stopping and uninstalling

Each way of stopping leaves a different amount running:

| Action | What stops | What keeps running |
| --- | --- | --- |
| `prefix+q` (detach) | This dashboard only | The daemon, every session, and active turns |
| **Suspend session…** (`prefix+shift+x`) or `mj suspend --session <id>` | That session's agent and target; a recovery copy is saved for **Resume** | The daemon and other sessions |
| `mj daemon stop` | The daemon | Session workers and their targets, including EC2 instances; the next `mj` reconnects to them |
| **Destroy session…** or `mj destroy --session <id>` | That session, its target, its clone, and its recovery copy, permanently | The daemon and other sessions |

To stop everything, suspend or destroy each session first, then run
`mj daemon stop`. `mj sessions` lists what is still live.

To uninstall after that:

1. Remove the programs. The release installer put `mj`, `mj-desktop`,
   `mj-voice-worker`, and the `mj-worker*` files in `~/.local/bin` (or
   `MJOLNIR_INSTALL_DIR`). For npm, run `npm uninstall -g @brokkai/mjolnir`.
2. Remove the configuration directory: `~/.config/mjolnir` on Linux, or the
   path in `MJ_CONFIG_DIR`.
3. Remove the data directory, which holds the session database, recovery
   archives, logs, and project memory: `~/.local/share/mjolnir` on Linux, or
   the path in `MJ_DATA_DIR`. Deleting it deletes every suspended session.
4. Remove the cache, which holds Git mirrors and the pinned agent installs:
   `~/.cache/mjolnir`, or `$XDG_CACHE_HOME/mjolnir` when that is set.
5. In each repository you used, delete the `.mj` folder, which holds only the
   session clones: `rm -rf .mj`. Sessions made by older Mjolnir versions used
   linked worktrees under `.mj/worktrees` on `mj/<id>` branches; remove those
   with `git worktree remove` first, and delete the `mj/<id>` branches you no
   longer want.

On macOS the configuration and data directories are both
`~/Library/Application Support/mjolnir`.
