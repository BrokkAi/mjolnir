> Fixture, CLI surface, and screenshots produced against Mjolnir 1.11.3 on
> 2026-08-20. Live provider output is model- and availability-dependent and is
> not run in docs CI.

This evaluation uses the coding team you select — Codex, Claude, or a mixed
team — against a checked-in Python fixture in a disposable Git repository.
The point of the exercise is not "the agent edits a file": it is watching
Mjolnir keep the work isolated in a linked worktree, delegate a bounded change
to a background subagent, challenge every changed turn with an independent
cross-provider review that validates its own findings before showing them,
and hand the same session between your terminal and a browser.

It does not prove large-repository performance, consistent quality across
models, predictable provider cost, safe unattended shell execution, or
remote-server security.

## Before you start: install and connect a team

Everything in this evaluation runs on a team you set up once, so do the setup
first, up front. You need Python 3 for the fixture tests, Git, and a Codex or
Claude account — ideally both, because the mixed teams are the interesting
ones here: the provider that wrote the change is never the provider that
reviews it. Provider use may cost money.

### 1. Install Mjolnir

Any route from [Install and run](/install/) works; the quickest:

```bash
npm install -g @brokkai/mjolnir
```

```bash
mj --version
```

### 3. Choose the team

Onboarding's **Team** tab (later: the same tab in `/mjconfig`) offers four
configurations: **Codex**, **Claude**, **Codex coder + Claude reviewer**, and
**Claude coder + Codex reviewer**. A team pins the primary seat to its coder
and the review and subagent seats to its reviewer while keeping all three
models on Auto.

With both providers signed in, Mjolnir defaults to **Claude coder + Codex
reviewer** so review lands on the model that did not write the code. With one
provider, that provider's own team is the default — every journey below still
works, but the reviewer then shares the coder's provider. This page's
screenshots come from a **Claude coder + Codex reviewer** run.

### 4. Confirm the seats

Before starting the journeys, check onboarding (or `/mjconfig`) reports your
provider signed in and its ACP server enabled, and that **Discrete review**
is on — the evaluation depends on it. After launch, `/agents` records the
model and adapter that actually bound to each seat, and the status line shows
the resolved primary model. Team changes apply to the next session.

## Prepare the disposable fixture

From a Mjolnir checkout:

```bash
EVAL_DIR="$(mktemp -d)/mjolnir-eval"
cp -R docs/fixtures/ten-minute-evaluation "$EVAL_DIR"
cd "$EVAL_DIR"
git init
git add .
git -c user.name="Mjolnir Eval" \
    -c user.email="mjolnir-eval@example.invalid" \
    commit -m "Add weather status and Fahrenheit helpers"
python3 -m unittest -v
```

If you are reading the published docs, clone the repository first:

```bash
git clone https://github.com/BrokkAi/mjolnir.git
cd mjolnir
```

The baseline has three passing tests over two small helpers, `status()` and
`fahrenheit()`. That is deliberately boring: the journeys below are about
what Mjolnir wraps around the work, not the work itself.

## Journey 1: an isolated worktree and a delegated change

Start Mjolnir in a linked Git worktree:

```bash
mj --worktree
```

On first use it offers to add `.mjolnir/worktrees/` to `.gitignore`; accept.
The status line shows the generated worktree name (for example
`.mjolnir/worktrees/bright-oak/`). Everything the session changes lands in
that worktree — your checkout stays untouched.

Send this prompt:

```text
Use the create_subagent tool from the mj-subagents MCP server to delegate
this bounded change to a background subagent, then end your turn without
waiting for it: update weather.py so status(0) returns "freezing", negative
values return "below freezing", values below 20 return "cold", and all other
values return "warm". The subagent should add focused tests for the new
statuses, run python3 -m unittest -v, and report the result. Do not change
anything else yourself.
```

Naming the `create_subagent` tool matters: coding agents ship their own
in-process helpers, and a bare "launch a subagent" can route to those instead
of Mjolnir's delegated subagent seat.

Expected observations:

1. The primary agent launches the subagent and ends its turn instead of
   waiting — the prompt is immediately yours again.
2. A stable `Subagents` workflow row appears with elapsed time and
   running/done counts. The subagent runs on the subagent seat's provider —
   on a mixed team, the coder's counterpart rather than the coder.

7. Prove the isolation from another terminal, in the fixture directory:

```bash
git status --short && git worktree list
```

The main checkout reports no modified files; the change exists only in the
linked worktree.

The exact wording and tool sequence differ by model. If the primary ignores
the explicit delegation or the change is wrong, record the selected models and
adapter in your evaluation notes; that is a failed outcome, not a docs
failure.

## Journey 2: turn up the review

Journey 1 used the default **Quick** review depth: one independent reviewer,
then a validation pass over its findings. This journey makes the review earn
its keep, then raises the stakes.

Ask for a direct change with a deliberately lazy test:

```text
Add a describe(temp_c) function to weather.py that combines the existing
helpers: return the status word followed by the Fahrenheit reading in
parentheses, with the conversion shown to one decimal place. Reuse status()
and fahrenheit() exactly as they are - do not modify or reimplement them.
Add one focused test that describe(12) starts with "cold", then run
python3 -m unittest -v.
```

Because the primary edits files itself this time, each edit and shell command
arrives as a fully readable permission card — the diff it wants to apply sits
under the question:

<figure class="shot">
  <a class="shot__zoom" href={shotPermissionCard.src} aria-label="Open the full-size screenshot: a permission card over the diff">
    <Image src={shotPermissionCard} alt="A permission request card titled Edit weather.py with Deny, Allow Once, and Always Allow choices, drawn over the diff adding the describe() function." />
  </a>
  <figcaption>Nothing is applied behind your back: the card sits on top of the exact diff, and Deny is the default.</figcaption>
</figure>

In our run the quick review answered that lazy `startswith` test with a
validated `P2` — the assertion cannot detect a malformed reading — which the
very next turn then had to address. Findings vary by model; what is stable is
that every workspace-changing turn gets this challenge before it is released.

Now raise the depth. Open `/mjconfig`, go to the **Reviewer** tab, and set
**Review depth** to **Extended** — the adversarial supervisor with on-demand
Norse specialist lanes. It costs far more tokens and applies from the next
dispatch:

<figure class="shot">
  <a class="shot__zoom" href={shotConfigReviewer.src} aria-label="Open the full-size screenshot: the /mjconfig Reviewer tab">
    <Image src={shotConfigReviewer} alt="The /mjconfig Reviewer tab: review model on auto via codex-acp, Codex session options, the discrete review toggle, and Review depth set to Extended." />
  </a>
  <figcaption>The <strong>Reviewer</strong> tab owns the other provider's seat: its model, its session options, the discrete-review toggle, and the Quick/Extended depth.</figcaption>
</figure>

Send a small follow-up (for example, round the Fahrenheit reading in
`describe()` to a whole degree). The `Review` workflow row now walks through
the extended pipeline — intent analysis, a supervisor, specialist lanes, and
correction rounds when a finding sticks:

<figure class="shot">
  <a class="shot__zoom" href={shotExtendedVerdict.src} aria-label="Open the full-size screenshot: the extended review verdict">
    <Image src={shotExtendedVerdict} alt="The extended review outcome, including the primary's review decision and the completed Review workflow state." />
  </a>
  <figcaption>The part worth paying for: the supervisor and specialists leave a visible, evidence-backed decision for every finding instead of silently discarding it.</figcaption>
</figure>

Findings are session-state, not scrollback. **F9** opens the evidence ledger:
it keeps the complete reviewer finding, the primary correction report, the
captured correction diff, and whether a later review independently verified
the correction. A workspace change alone is shown as **corrected — verification
pending**, never as fixed.

<figure class="shot">
  <a class="shot__zoom" href={shotReviewLedger.src} aria-label="Open the full-size screenshot: the F9 review issue ledger">
    <Image src={shotReviewLedger} alt="The session review ledger, which records each reviewer finding and its correction or verification state." />

</figure>

One scope note to calibrate expectations: discrete review judges **the turn's
diff** against your instructions. It reads surrounding code as context, but
it is not a whole-repository audit — pre-existing defects in files a turn
never touched are out of its jurisdiction.

## Journey 3: leave the desk, keep the session

Mjolnir Web publishes the same sessions to a browser. In a second terminal:

```bash
mj server
```

When the machine is on a tailnet with MagicDNS and HTTPS certificates
enabled, the server detects it, serves a trusted certificate for the
machine's `ts.net` name, and prints a QR code plus a six-digit viewer code —
scan it from your phone anywhere on the tailnet. Without tailscale (or with
`--no-tailscale-detect`) it binds `https://localhost:11921` with a
self-signed certificate and explains why the QR is hidden. `--port` changes
the port; local `mj` sessions follow it automatically.

    <Image src={shotServerTailscale} alt="mj server startup output: a trusted certificate obtained for the machine's ts.net name, a login QR code, and a six-digit viewer code. QR, hostname, and code are redacted in this screenshot." />

  <figcaption><code>mj server</code> with tailscale detected: trusted TLS for the machine's <code>ts.net</code> name and a QR sign-in for your phone. (Hostname, QR, and viewer code redacted here.)</figcaption>
</figure>

Sign in with the viewer code. The running TUI session from the journeys above
is already in the session list — same transcript, same review results, same
permission prompts. The `P2` has already gone through its automatic correction
attempt. Inspect its recorded evidence from the browser:

```text
Open the review ledger and summarize the P2's correction report and
verification state.
```

The browser is the same session, not a copy — Journey 2's review recap and the
<code>P2</code>'s correction evidence are both available there.

Back at the terminal, exit with **Ctrl-D** on an empty prompt. Mjolnir asks
whether to keep or remove the worktree, then prints the way back:

```text
To resume: mj resume <session-id> --worktree <name>
```

Run the printed command. The session returns through its saved ACP adapter and
model provenance — including the turn you ran from the browser. That is the
whole loop: start at the desk, continue from a phone, come back to the
terminal.

## Voice

On supported desktop platforms, **Ctrl-R** starts locally transcribed
dictation straight into the prompt — no audio leaves the machine. Try it on
any of the journey prompts above; see [Voice dictation](/voice/) for platform
support and model download details.

## Interpret the result

A successful run proves the selected team can, on one small repository: keep
agent changes out of your checkout, delegate and supervise background work,
challenge every changed turn with a validated cross-provider review, and move
one session between terminal and browser. Record model IDs, elapsed time,
token/cost telemetry, whether the delegation occurred, what each review pass
raised and how the validator disposed of it, and any manual intervention.
Then repeat with another team from `/mjconfig` — the mixed teams are the
quickest way to watch one provider's reviewer challenge the other provider's
change.

Before broader use, read [Permissions and workspace scope](/permissions/) and
[Data and trust boundaries](/data-boundaries/).
