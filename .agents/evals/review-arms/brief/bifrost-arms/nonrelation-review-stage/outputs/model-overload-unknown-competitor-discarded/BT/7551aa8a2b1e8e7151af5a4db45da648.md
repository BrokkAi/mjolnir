- [P1] Preserve uncertainty when another overload cannot be classified — crates/bifrost-analysis/src/analyzer/usages/call_conversion.rs:837-838
  When one overload has a proven conversion but another returns an unknown such as `UnresolvedTargetType` or `GenericSubstitution`, this selects the first overload as exact even though the second may also apply or be the actual Java overload. Policies can consequently attribute a call to the wrong modeled member. A failed proof must be distinguished from a proven inapplicable candidate before a unique selection is made.
- [P2] Do not apply scalar conversions to array elements — crates/bifrost-analysis/src/analyzer/java/call_conversion.rs:467-468
  For array arguments this recursively applies scalar primitive widening and boxing, so, for example, `int[]` is reported convertible to `long[]` or `Integer[]`, although Java permits neither conversion. This can select an inapplicable modeled overload and produce incorrect conversion evidence; array conversion needs its own rules.
- [P2] Preserve parameter names in compatible named layouts — crates/bifrost-analysis/src/analyzer/semantic_model/overlay.rs:2295-2298
  For non-Java overload families with positional-or-keyword parameters, signatures whose corresponding names differ are now considered compatible. A positional call then takes the first signature's formal names in the compatible-layout path, even though the selected overload is unknown, so `formal_name` bindings and policies can point to the wrong parameter. Names must remain part of layout compatibility when callers or consumers can observe them.
