- [P1] Preserve uncertainty from other overload candidates — crates/bifrost-analysis/src/analyzer/usages/call_conversion.rs:837-838
  When one overload has a provable conversion but another has an unresolved target type or unsupported conversion, this returns the first overload as exact and discards the failure. The rejected candidate may also be applicable or more specific, so policies can select the wrong modeled member and produce false positives or negatives. A failed proof is not evidence that the candidate is inapplicable.
- [P1] Do not apply scalar conversions to array elements — crates/bifrost-analysis/src/analyzer/java/call_conversion.rs:467-468
  For array arguments this recursively applies scalar widening and boxing rules, so, for example, `int[]` is accepted for `long[]` or `Integer[]`, neither of which is a Java method-invocation conversion. This can select an inapplicable modeled overload and emit incorrect conversion facts.
- [P2] Preserve formal names for named-capable overloads — crates/bifrost-analysis/src/analyzer/semantic_model/overlay.rs:2295-2298
  For non-Java callable families with positional-or-named parameters, two overloads whose corresponding formal names differ are now considered layout-compatible. A positional call then uses the first overload's formal name even though the other overload is equally possible, so downstream bindings and policies can claim a specific parameter mapping that is not established.
