- [P1] Preserve uncertainty from other overload candidates — crates/bifrost-analysis/src/analyzer/usages/call_conversion.rs:821-829
  When one overload converts successfully but another has an unresolved type, generic substitution, or another unsupported conversion, the latter is discarded and the first is selected as unique. An unknown conversion does not prove that the other overload is inapplicable; for example, an unmodeled subtype relationship or generic overload can also accept the argument. This can attach an exact model identity and policy behavior to the wrong overload instead of reporting incomplete selection.

- [P1] Do not apply scalar conversions to array elements — crates/bifrost-analysis/src/analyzer/java/call_conversion.rs:467-468
  For array arguments this recursively applies scalar widening, boxing, and unboxing, although Java does not convert `int[]` to `long[]` or `Integer[]`. Consequently a modeled overload taking one of those array types can be selected and reported as an exact binding for a call that does not invoke it, producing incorrect policy results.

- [P2] Retain formal names when comparing keyword-capable layouts — crates/bifrost-analysis/src/analyzer/semantic_model/overlay.rs:2295-2298
  For non-Java overload families with positional-or-named parameters, two signatures with different formal names now receive `CompatibleLayout`; the binding path then uses the first signature's names for every positional call. For example, overloads `f(value)` and `f(items)` can produce an exact binding to `value` even when the selected overload's formal is `items`, causing name-based policy selectors to match the wrong parameter or miss the correct one.
