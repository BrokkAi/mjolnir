- [P1] Preserve Rust assignment evaluation order — crates/bifrost-analysis/src/analyzer/rust/semantic.rs:2135-2136
  For an indexed assignment whose right-hand side and index have side effects, Rust evaluates the right-hand side before evaluating the assignee, but inserting the base and index at the front schedules them first. For example, `values[next_index()] = produce()` is modeled as calling `next_index` before `produce`, which can reverse data flow and reachability when either call mutates state or exits early. Field assignments have the same ordering problem.

- [P2] Do not infer absence of Drop from one file — crates/bifrost-analysis/src/analyzer/rust/semantic.rs:4115-4118
  A `Drop` implementation can be declared in another module of the same crate. For example, a plain-looking `struct Guard {}` in this file can have `impl Drop for Guard` in a sibling module; a `Guard {}` local is then classified as non-dropping and its scope exit omits the destructor call and cleanup gaps. The file-local scan cannot prove that no such implementation exists.

- [P2] Resolve struct names before treating field accesses as direct projections — crates/bifrost-analysis/src/analyzer/rust/semantic.rs:4063-4069
  When a different module in the file declares a struct with the same unqualified name as the type used by a procedure, this table can select that unrelated declaration even if the actual type comes from an import in another file. A field access is then assigned the wrong member identity and its implicit `Deref` and field-identity gaps are suppressed, so stores and loads can be attributed to the wrong field and calls can disappear from the analysis.
