- [P1] Evaluate the right-hand side before the assignment place — crates/bifrost-analysis/src/analyzer/rust/semantic.rs:2103-2103
  For a field assignment with side effects in both operands, Rust evaluates the right-hand side before evaluating the assignee, but inserting the base at the front reverses that order; the index branch similarly puts both base and index before the right-hand side. For example, `get_holder().field = compute()` is modeled as calling `get_holder` before `compute`, so control and value-flow results can report effects in an order the program cannot execute.

- [P1] Do not infer an overloaded operator's result from its operands — crates/bifrost-analysis/src/analyzer/rust/semantic.rs:1156-1161
  When a non-dropping type implements an operator whose `Output` has a destructor, such as a plain `struct Token` whose `Add` returns a guard, `let guard = a + b` is marked non-dropping because both operands are non-dropping. The resulting scope-exit and replacement facts omit the guard's actual `Drop` call and cleanup behavior, making subsequent analysis incorrectly complete.

- [P2] Resolve the callee before assuming its return type — crates/bifrost-analysis/src/analyzer/rust/semantic.rs:1224-1231
  When a local callable shadows a same-file function, the function-name lookup can attribute the unrelated function's primitive return type to the local call. For example, a closure named `make` returning a guard can shadow `fn make() -> i32`; `let guard = make()` is then treated as non-dropping and its destructor and associated cleanup gaps are omitted.
