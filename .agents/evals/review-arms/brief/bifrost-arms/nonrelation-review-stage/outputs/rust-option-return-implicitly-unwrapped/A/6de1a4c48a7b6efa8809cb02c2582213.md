- [P2] Resolve field types in the field's module first — src/analyzer/usages/get_definition.rs:1094-1095
  When a field's declared type name is also imported in the calling file for a different type, resolving the field signature against the caller first selects the caller's import and never checks the field's own module. For example, `outer.inner.name` can resolve `name` on an unrelated `Inner`, or report it missing, even though the field declaration identifies the correct type in its own imports.
- [P2] Preserve return types of user-defined unwrap methods — src/analyzer/usages/get_definition.rs:984-993
  When a project type defines its own `unwrap` or `expect` method returning a different type, this branch treats the call as returning the receiver type and bypasses the indexed method signature. Consequently, a lookup such as `wrapper.unwrap().field` resolves against `Wrapper` instead of the actual return type, potentially returning a wrong definition or no definition.
- [P2] Distinguish method calls inside macro token trees — src/analyzer/usages/get_definition.rs:658-662
  When a macro argument contains a method call and the receiver type has a field and method with the same name, this path always filters for fields. A lookup on `value.name()` inside the macro therefore returns the field definition even though Rust resolves the call to the method.
