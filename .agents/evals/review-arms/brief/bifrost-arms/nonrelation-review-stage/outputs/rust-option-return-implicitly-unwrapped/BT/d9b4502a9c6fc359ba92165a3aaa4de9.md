- [P2] Resolve field types in the declaring file's context first — src/analyzer/usages/get_definition.rs:1094-1095
  When a field's type name is imported differently in the caller and the field's declaring module, the new import-aware lookup resolves the signature using the caller's import and never checks the declaring module. For example, if `Holder.item` is declared as `model::Item` via an import in its module but the caller imports a different `Item`, lookup of `holder.item.name` can return the other type's `name` field. The type text belongs to the field declaration and must be interpreted in that file's context.
- [P2] Do not treat every unwrap or expect method as a container operation — src/analyzer/usages/get_definition.rs:984-993
  When a user-defined type has an `unwrap` or `expect` method returning another type, this branch infers the receiver's type instead of consulting the method's return signature. Consequently, `let value = wrapper.unwrap(); value.field` resolves against `Wrapper` rather than the actual returned type, potentially reporting the wrong field or no definition; the previous general method-call path could resolve this case.
- [P2] Preserve Option as the receiver type until it is unwrapped — src/analyzer/usages/get_definition.rs:1062-1063
  When a function returns `Option<Foo>` and its result is used directly as a method receiver, such as `make().is_some()`, this unconditionally infers `Foo` as the receiver. If `Foo` defines a method with the same name, lookup incorrectly reports that method as the definition of the `Option` method. Unwrapping must depend on the surrounding operation rather than the return signature alone.
