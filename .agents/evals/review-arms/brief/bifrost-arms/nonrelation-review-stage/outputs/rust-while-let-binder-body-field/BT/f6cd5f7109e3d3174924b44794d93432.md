- [P1] Preserve bindings in while-let loops — crates/bifrost-rust/src/structural.rs:427. For `while let Some(x) = value { ... }`, the Rust grammar names the loop block `body`, not `consequence`, so this returns `None` and drops the pattern binding. The shared environment then reports unknown binding activation for the file and cannot resolve uses of `x` in the loop, regressing all consumers of that environment.
- [P2] Include later let-chain conditions in binding activation — crates/bifrost-rust/src/structural.rs:427-431. In a Rust let chain such as `if let Some(x) = opt && x > 0 { ... }`, `x` is also in scope in subsequent conditions. Restricting activation to the consequence makes that reference unresolved or incorrectly resolves it to an outer `x`, so lexical consumers receive the wrong binding identity.
- [P2] Do not treat discarded literals as branch results — crates/bifrost-analysis/src/analyzer/branch_boolean.rs:87-88. The wrapper loop also unwraps Rust expression statements, so valid code such as `if c { true; } else { false; }` now produces a redundant Boolean return finding even though both branches evaluate to `()` and neither returns a Boolean. The same issue affects a discarded literal following an `if` without an else.
- [P2] Preserve existing findings for Boolean conditions — crates/bifrost-analysis/src/analyzer/structural/branch_relations.rs:330-333. Valid Rust conditions such as `x > 0`, `predicate()`, or `if let Some(_) = opt` are rejected by `rust_boolean_expression`, so previously supported patterns like `if x > 0 { return true; } else { return false; }` silently stop producing findings. Rust requires an if condition to be Boolean, and the policy does not require a proof that evaluating the condition is effect-free.
