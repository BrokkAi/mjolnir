- [P1] Include all requested overloads in the graph search — src/usages/csharp_graph.rs:43-43. When callers pass multiple overloads, the strategy builds its specification solely from the first one and filters calls by its arity, then returns success. Calls to the other overloads are silently omitted and the regex fallback never runs.
- [P1] Route fully qualified static accesses to the graph — src/analyzer/csharp_analyzer.rs:303-307. A file containing only an expression such as `Domain.Target.Run()` has no using directive or type-position reference to `Domain.Target`, so it is absent from the reverse index and from `type_identifiers`. The default candidate provider consequently excludes it, and usage lookup returns a successful result without that call even though the graph can resolve the expression when given the file.
- [P2] Account for optional and variadic arguments — src/usages/csharp_graph.rs:324-329. A constructor with optional parameters or a `params` array can legally be called with a different number of arguments than its declared parameter count; this check discards those calls and returns success. The equivalent arity check for methods has the same problem.
- [P2] Resolve namespaces at the reference location — src/analyzer/csharp_analyzer.rs:155-159. A C# file can declare several namespaces, but this picks an arbitrary declaration's namespace for the entire file. References in another namespace in the same file can therefore resolve to the wrong same-named type or be omitted, and the same approximation also affects candidate routing.
- [P2] Do not infer a variable's type from nested creations — src/usages/csharp_graph.rs:545-555. For `var x = Wrap(new Target());`, this recursive search infers `x` as `Target` even though its type is the return type of `Wrap`. A subsequent `x.Run()` is then reported as a certain usage of `Target.Run`, including when `Wrap` returns an unrelated type.
