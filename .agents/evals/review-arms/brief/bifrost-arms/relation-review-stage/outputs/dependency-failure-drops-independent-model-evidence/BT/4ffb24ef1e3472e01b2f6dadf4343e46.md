- [P1] Require Java dependency proof before reporting absence — crates/bifrost-analysis/src/analyzer/java/diagnostics.rs:81-88. When any overlay exists, including an empty overlay or one activated for Python only, an unknown Java type becomes an error. Overlay presence does not prove that Java dependency discovery completed, and this branch does not search the overlay for the type. Valid types supplied by Java packs can therefore be reported as missing, as can types from dependencies that were never discovered.

- [P1] Resolve type parameters before reporting missing types — crates/bifrost-analysis/src/analyzer/java/diagnostics.rs:60-64. In a generic declaration such as `class Box<T> { T value; }`, the use of `T` is a type identifier, but the workspace type lookup does not resolve lexical type parameters. When an overlay is present and external lookup returns unknown, the valid use is reported as an unrecognized Java type.

- [P1] Publish the persistent active set only after overlay construction succeeds — crates/bifrost-analysis/src/analyzer/semantic_model/runtime.rs:1454-1464. If overlay construction is cancelled or exceeds its retained-byte limit, this path returns a failure after replacing the persistent active set. The old in-memory overlay remains active while the catalog records the new set, so subsequent readers and restarts can observe a different activation from the one reported to the caller. The newly resolved path has the same ordering.

- [P2] Keep dependency discovery out of diagnostic requests — crates/bifrost-analysis/src/analyzer/java/diagnostics.rs:71-71. The first unresolved Java type initializes the external index, which runs JVM dependency discovery and reads artifacts without a cancellation token. A diagnostic request can therefore block the LSP on a large dependency tree even when no dependency activation was requested.
