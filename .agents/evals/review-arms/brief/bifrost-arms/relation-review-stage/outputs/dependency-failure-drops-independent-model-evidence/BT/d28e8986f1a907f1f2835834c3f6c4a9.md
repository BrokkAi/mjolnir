- [P1] Require JVM proof before reporting a missing type — crates/bifrost-analysis/src/analyzer/java/diagnostics.rs:81-88. Any semantic overlay triggers an absence diagnostic, even when it contains only Python models or has no JVM discovery evidence. The collector also does not search the overlay for the requested type. A valid Java dependency supplied by an active pack can therefore produce an unrecognized-type error, and an unrelated overlay can turn unknown classpath results into false errors.
- [P1] Preserve persistent state when overlay construction fails — crates/bifrost-analysis/src/analyzer/semantic_model/runtime.rs:1454-1464. When persistence is configured, this replaces the stored active set before overlay construction. Cancellation or a retained-byte limit can then make construction fail while the previous in-memory overlay remains active. A later reader of the stored active set sees the failed replacement. The same ordering occurs on the newly resolved path.
- [P2] Replace evidence when replacing the overlay — crates/bifrost-analysis/src/analyzer/semantic_model/runtime.rs:1020-1032. Activating Python and then JVM separately replaces the entire overlay but retains the Python discovery evidence. Calls through the existing activation API also replace the overlay without clearing any evidence. Consumers can therefore see complete evidence for an ecosystem whose packs are no longer in the active overlay.
- [P2] Keep dependency discovery out of Java diagnostic requests — crates/bifrost-analysis/src/analyzer/java/diagnostics.rs:71-71. The first unresolved type initializes the JVM external index, which performs dependency discovery and artifact scanning without a cancellation token. With semantic diagnostics enabled, an ordinary edit can therefore block diagnostic publication on project-wide package I/O.
