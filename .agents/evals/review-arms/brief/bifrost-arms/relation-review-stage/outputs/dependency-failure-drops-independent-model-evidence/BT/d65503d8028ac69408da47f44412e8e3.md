- [P1] Require JVM proof before reporting an absent type — crates/bifrost-analysis/src/analyzer/java/diagnostics.rs:81-88. When any semantic overlay exists, this branch reports an unknown Java type as absent without checking whether the overlay contains JVM packs or whether JVM discovery completed. A Python-only or empty overlay can therefore cause errors for valid Java dependencies. The branch also does not look up the type in the overlay, so even a JVM pack that contains the type cannot prevent the error.

- [P1] Keep persistent activation unchanged when overlay construction fails — crates/bifrost-analysis/src/analyzer/semantic_model/runtime.rs:1454-1464. When persistence is enabled, `publish_active_models` replaces the persisted active set before overlay construction. If construction is cancelled or exceeds a limit, the function returns failure and retains the old in-memory overlay, but the persisted active set already contains the new models. A later reader or restart can therefore observe an activation that the caller was told failed. The newly resolved path has the same ordering.

- [P2] Avoid dependency discovery during Java diagnostics — crates/bifrost-analysis/src/analyzer/java/diagnostics.rs:71-71. On the first unresolved Java type, this call initializes the external index, which runs JVM dependency discovery with default limits and no cancellation token. A diagnostic request can therefore scan dependency artifacts and block the LSP, including when no dependency proof has been activated. The diagnostic path needs to read retained evidence instead.
