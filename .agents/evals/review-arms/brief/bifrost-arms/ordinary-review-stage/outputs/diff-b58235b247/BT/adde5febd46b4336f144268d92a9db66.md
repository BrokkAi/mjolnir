- [P2] Follow Python's method resolution order for multiple inheritance — crates/bifrost-python/src/graph/resolver.rs:59-64
  When a receiver inherits from multiple bases, breadth-first traversal does not implement Python's C3 method resolution order. For example, if `C(A, B)` and both bases define `save`, `C().save()` resolves only to `A.save`, but this returns both declarations; if `A` inherits `save` and `B` defines it, the breadth-first search can select `B.save` even when Python selects the inherited declaration through `A`. Usage results therefore include the wrong method and can omit the actual one.
- [P2] Respect inner function declarations when selecting an outer import — crates/bifrost-analysis/src/analyzer/usages/get_definition/python.rs:1954-1961
  If an outer function imports `name` and an inner function declares its own `def name(): ...` before referencing it, the outer import passes the scope-range filter and `has_runtime_callable_binding_at` does not count function declarations. The new early return then resolves the reference to the imported symbol instead of the inner function, bypassing the existing lexical resolution path.
- [P2] Check the importlib binding at the assignment site — crates/bifrost-python/src/imports.rs:60-62
  If `importlib` is rebound before the assignment and restored before the reference, such as `importlib = fake; mod = importlib.import_module("pkg"); import importlib; mod.member`, the callback checks visibility at the later reference and attributes `mod.member` to `pkg` even though the call used `fake`. This produces incorrect usage and graph edges for the workspace module.
