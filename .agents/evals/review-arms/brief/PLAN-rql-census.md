# Which RQL facts help reviewers? A Rust census and a mocked-RQL writer

Status: approved by Jonathan and registered on 2026-11-18, before any census label, simulator answer or reviewer run. Advisor input (91233b0e, two rounds) is folded in; its notes are in `rql-census/prep/advisor-notes.md`. Preparation artifacts (the public-repo scouting and the local corpus yield screen with its script) are in `rql-census/prep/`.

## Question

Milestone 5 of `.agents/plans/review-brief-writer.md` would give the brief writer RQL (Bifrost's code query language), not a hardcoded tool. Two questions decide whether to build the RQL features that would need:

1. **Census.** Across real Rust bugs, which relation decides each one, could an RQL query express it, and does today's Bifrost return it? This ranks candidate features by how many bugs they decide, needs no reviewers, and is reported as a ceiling.
2. **Mocked RQL.** If a writer could query a complete RQL, would its briefs lift Terra/high reviewers over a grep-only writer? Real RQL isn't complete yet, so a simulator answers. Its answers must be reasonable and complete, not prescient.

A positive result shows that the information helps when it's delivered this way. It doesn't show an engine is required: the compute-matched arm and the simulator's cost and latency set the bar real RQL must beat.

## Data

**Repositories.**
- Development: mjolnir and bifrost-dev, with their frozen corpora.
- Test: 12 Rust repos (fewer if fewer qualify), fixed before any test reviewer runs. Clones that share history (a common commit or root, such as forks, renamed repos or subtrees) count as one repo; the screen groups them by shared candidate commits and root commits. Every member stays ranked, and selection takes at most one per group. Repos come from the local corpus (`~/Projects/brokkbench/sft-tools-commits/rust`, clones in `/nfs/morannon/nvme/repo-clones`, read only). Jonathan chose fewer repos with more bugs each, because Bifrost indexing is expensive per repo.
- Selection rule: rank by realistic 2025+ yield from the screen (`rql-census/prep/scan.py`, then `yield_rank.py`, which turns the capped samples into per-repo yields: upper bound × bug precision 0.85 × admission rate 31/67; results in `yield.json` and `corpus-yield-summary.md`). The screen applies the corpus size rule (goldens, fixtures and lock files don't count) and rejects merge commits as introductions. Incompletely traced fixes never count as strong, and the ranker refuses to rank while any planned draw lacks a trace record. File paths come from Git's NUL-separated name list, not patch headers. Functions are counted from the old file's `fn` signatures, so the screen doesn't depend on a repo's diff drivers. Drop repos with indexing hazards: huge generated code, a non-Cargo build, heavy proc-macro output. The screen only orders repos: its multi-site proxy over-counts (for example, inline `#[cfg(test)]` hunks in production files), so a repo enters the test set only after tracing admits at least 8 relation diffs, going down the ranked list. Inputs are reproducible: `stage_a.py` derives `stage_a_candidates.jsonl.gz` from the SFT lists, then `scan.py` and `yield_rank.py` run on it.
- Rank and measure at least 16 repos: one cold Bifrost index and one warm restart after about 50 commits, at a representative revision (`measure_index.py`). Measurements run on an EC2 host, never the user's workstation, inside a cgroup memory cap (`systemd-run --user -p MemoryMax=48G -p MemorySwapMax=0`), pinned to the commits in `index-pins.txt`. The batch ran `measure_index.py` as committed at 676f6d7f2. Later revisions changed teardown, cancellation, input checks and the record-reuse key, not the readiness rule or the CPU accounting. That revision didn't record the measurement environment, so it is stated here: every run was on one m8id.4xlarge instance (16 vCPUs) in a single boot, the scopes set only memory limits (no CPU quota), and no Bifrost or Rayon thread settings were present. A repo whose index exceeds the cap is recorded as a failed measurement. gitbutlerapp/gitbutler is excluded: its index grows without bound from a Bifrost defect (bifrost-dev #14480), which crashed the workstation twice on 2026-11-18. It may re-enter once #14480 is fixed and it measures under the cap. Excluding that file, gitbutler indexes at a 3.2 GiB peak. The batch records each server's whole-tree peak memory, OOM result and tree CPU, so any further blow-up is captured and contained. Indexing hours are the study's workload, in CPU-hours of the server's whole process tree up to its ready reply (`cpu_to_ready_usec`, from the scope cgroup), not wall time: one cold index plus one warm restart for each further expected bug revision. That is cold + (B − 1) × warm, where B is the capped expected bugs. Take the 12 that qualify with the most expected admitted bugs, B, using each repo's conservative relation-diff estimate capped at the tracing stop of 25 (`per_repo_relation_estimate_capped` in the 2025+ window: the all-bug estimate × 17/30, bifrost-dev's relation share, counting distinct introducing changes), at most one per shared-history group (`select_cohort.py`). A failed measurement excludes the repo: pola-rs/polars exceeded the cap (#14480) and PerryTS/perry's analyzer store failed with a SQLite size error (bifrost-dev #14536). Revised 2026-11-19, before any reviewer run and before tracing beyond the first four repos: this replaces the registered ranking by bugs per indexing hour, B / (cold + (B − 1) × warm). That rule assumed indexing was costly. The measurements put most cold indexes at 1 to 18 CPU-minutes and the study's indexing at about 12 CPU-hours across 17 repos, so cost no longer separates repos. Cost weighting ranked repos expecting about 2 to 4 relation diffs, such as j178/prek, above three of the four highest-yield repos, against the reason for choosing fewer repos with more bugs. Index CPU-hours are still reported and break ties. The estimates run low: rspack, estimated at 13, reached 25 confirmed relation diffs. Every member of a group stays ranked, so a related clone remains eligible if the yield leader is costly to index or disqualified. Reaching ±10 needs about 12 repos if the between-repo SD is 10 points, and about 16 if it is 15. More bugs per repo can't substitute for more repos. If fewer than 12 qualify, use all that do; a wider interval then reads as the bands below say.
- A repo counts only if it has at least 8 distinct admitted relation diffs, decided before any reviewer runs on it. Diffs are counted by introducing change: several fixes of one introduction form one diff, carrying the union of their decisive facts. When one introduction has several known defects, the relation defects define the diff's primary catch. A review catches the diff when it identifies any of its relation defects, and the judge gets every relation-defect record and names every one the review matched. The diff-level catch is derived from those matches (any match), and the census uses each defect's own matches. Its local, non-relation defects earn no primary credit; they count only in the non-relation controls. The corpus spread rule (at most two diffs per feature or commit series) still applies.

**Bugs.**
- Candidates come from each selected repo's full git history: fix commits that change non-test code and add or change a test. Each repo's eligible fixes are traced in a seeded random order (seed 20261118), stopping when the repo reaches 25 distinct admitted relation diffs (introducing changes) or the pool runs out. Local defects admitted along the way are kept for the non-relation controls but don't count toward the stop. This is the same unit as the screen's capped yield. The order and the stopping point are recorded. The brokkbench SFT lists only seeded the screen, and they are a model-screened subset capped at 1,000 commits per repo.
- The corpus SPEC rules (`corpus/SPEC.md`) apply, adapted: the regression test in the fix commit replaces the Hard-won marker, and the cutoff rule becomes the window below. The ordinary-commit rule uses each repo's default branch (the clone's HEAD branch, `main` or otherwise) in place of `master`. Attribution, findable-from-the-diff, real behavior, not pre-flagged, size and spread all apply unchanged.
- Each candidate is admitted by a tracer helper with a second-family check of the attribution and of the relation call, as in `PLAN-bifrost-bugs.md`. The tracer is Gemini neon/high, the user's current helper model; the check is a Claude Sonnet sub-agent of the coordinator, run against its own clones at the same pins after the tracer records each admission as pending. A disagreement isn't admitted, and the tracer then resumes that repo from its recorded stop index in the same seeded order, so verdicts don't change which candidates are traced. Tracing is git-history work only, with no indexing. The brief is `corpus-rust10/tracer-brief.md` (the pending-then-check flow and the later repos were sent as messages), and each repo's verdicts, with evidence, are in its `second-check.jsonl`.
- Target about 25 admitted bugs per repo.

**Window.**
- Test bugs have both the introducing change and the fix on or after 2025-01-01.
- If a candidate repo's 2025+ window can't reach the target, its test window extends to 2024-01-01 before its eligibility (the 8-diff floor) is judged, and before its development sample is drawn. The extension is recorded. The extended pool keeps the 2025 order as its prefix and appends the fixes that only the wider window admits, in seeded order. Fixes rejected earlier only because their introduction predates 2025 are re-evaluated at their original positions, so the stop still falls where the seeded order reaches the 25th relation diff. Rows past that stop are set aside, not counted.
- Contamination: a memorized bug tends to be caught in every arm, which shrinks the paired difference. An RQL row can also cue recall of a bug the reviewer missed without a brief, which inflates it, so the direction isn't guaranteed. Sensitivity checks are the after-cutoff subset (cutoffs: Sol 2026-04-30, Terra 2026-06-01, Opus June 2026) and the no-brief catch rate by fix date. The latter is descriptive only, because difficulty and repo mix confound it.

**Development and test split.**
- The RQL step menu is chosen only from development data: mjolnir, bifrost-dev and up to 10 bugs per test repo fixed before that repo's test-window start (before 2025, or before 2024 for an extended repo; census only). Development and test bugs therefore never overlap in time, and no introducing or fix commit appears in both sets.
- Development bugs are labelled for relation kind and expressibility only. That needs no indexing of old commits. They feed the menu counts and nothing else.
- Grammar, prompts and simulator tuning use mjolnir and bifrost-dev only.
- No 2025+ test bug informs the menu, the grammar or the prompts.
- **Menu rule, written before the development census:** the added steps are the top k = 3 missing step kinds, ranked by the repo-averaged share of relation bugs they decide. Labellers pick each missing step's kind from a fixed list in `label-SPEC.md` (value_flow, field_writes, call_arguments, guarded_path, state_lifecycle, keyed_matching, contract, other), so the ranking is mechanical. Bugs whose primary label is `not_confirmed` are left out of the tally. A kind decides a relation bug when, in the primary label, its recorded decisive set has every fact outside the diff either documented or missing with that kind, and at least one of the latter. The development task records one decisive set per bug, so a bug with separate explanations credits only the one the labeller recorded; this is a stated limitation of the menu, not a property of the steps. Each development repo's share is the fraction of its relation bugs the kind decides; the ranking averages those shares over the development repos (mjolnir, bifrost-dev, and each test repo with development bugs), breaking ties by the total number of bugs decided. `other` is never added.
- **Menu stability:** report whether the menu changes when one test repo's development bugs are left out, and when all of them are left out. This shows the menu is stable. It can't certify that no test information reached the frozen inputs: step semantics, query bounds or prompts could shift while the three step names stay the same. That protection is procedural. Nobody who shapes those inputs sees a test bug's census record, fix or decisive facts before the freeze.
- **Exclusion:** a test bug in the same family as a development bug from that repo is excluded. Same family means the same issue, or introduced by the development bug's fix.

## Stage 1: census (no reviewers)

Two labellers from different families (Sol/high primary, Opus/high replication) see the bug record, fix and introducing diff. Before the menu is computed and again before the readout, every saved label is revalidated with the final validator in `census_label.py`; a label that fails is set aside and labelled again. They label independently: the replication labeller runs on an isolated container target that holds only its own batch and checkout, so it can't read the primary's labels or raw outputs (`census_label.py`, `label-SPEC.md`). For each bug they record:
- **Decisive facts,** as minimal sufficient sets: several sets when more than one fact decides the bug.
- **Relation kind and RQL expression:** a documented step, a missing step (with its semantics), or not expressible. A documented step must return a row that states the fact, such as a value, an argument or a caller, as the missing steps this plan expects (value-flow endpoints, field writes with values, argument values) would. A query that only points at code a reader must open is recorded separately as the fact's locator query. Revised 2026-11-19, before any menu was chosen: an earlier labeller spec counted locating queries as documented, and on 92 development labels that left no missing steps, because documented RQL can point at almost any code site. That would have made the menu empty and the expressibility question meaningless. The 92 labels were set aside, and the development split is relabelled under this rule.
- **Anchoring:** whether the canonical query anchors on a symbol the diff touches, and the hops from it.
- **Row count:** how many rows the canonical query returns at the introducing commit. For documented steps it comes from running Bifrost. For a missing step it comes from the answer engine, once the menu is chosen, and so exists only for menu steps. Missing steps outside the menu are reported without row counts.
- **Bifrost today:** whether today's Bifrost returns the decisive row (run it), and whether it's complete.
- **Primary membership:** a bug is a relation diff when the primary labeller (Sol) records a decisive fact relating two or more code sites. A bug whose primary label is `not_confirmed` is adjudicated by hand before any reviewer runs, against the corpus's second-family check. If the defect isn't upheld, the bug leaves the test set, the menu tally and the recovery pilot, so no reviewer is scored against an unconfirmed claim and no such claim is supplied as an oracle fact. That includes relation bugs the menu can't express; the expressible subset is secondary. This is fixed before any reviewer runs, and labeller agreement is reported.
- **Baseline catch:** the share of the bug's 4 no-brief Terra reviewers who catch it, from stage 2's no-brief arm, using the hand-checked labels. "Among baseline misses" weights each bug by its no-brief miss share. A bug every reviewer missed counts fully, one with 1 catch of 4 counts 0.75, and one every reviewer caught counts 0. This rule is frozen before any no-brief outcome is read.

It reports:
- features ranked by bugs decided among baseline misses;
- for each fixed recipe ("run step S on every touched symbol") over a documented or menu step, the share of bugs whose decisive row it emits, against total rows emitted. That evaluates a pushed-facts brief without reviewers;
- agreement between the two labellers per category;
- a bias statement: bugs fixed soon after they were introduced lean toward visible regressions.

## Stage 2: mocked RQL

**Language.**
- Documented RQL at a pinned Bifrost commit, plus the missing steps that the development census ranks highest (expected: value-flow endpoints, field writes with values, argument values at call sites).
- Each added step's semantics are written down before any answer is generated: which constructs it crosses and to what depth.
- Queries must parse against the frozen grammar, with no free text.

**Answer engine.** It sees the post-change tree of the introducing commit only: no diff, no `.git`, no network. Its model is Claude Opus/high on the Claude profiles the coordinator allots, for both classification and value-flow hops. The gold set's second-family enumerator is Sol/high. Memorized fixes are a second route to prescience; the decisive-versus-other recall check covers that too.
- **Candidates:** Bifrost ∪ rust-analyzer ∪ identifier grep (for fields: `.name`, and `name:` in literals and patterns). Each row is tagged with its sources, which gives today's Bifrost recall against the union for free.
- **Classification:** a model classifies one candidate site at a time, from a few lines of context, with no diff and no other candidates. It copies value expressions verbatim, and a mechanical check confirms each is on that line. No paraphrase.
- **Value flow:** traced as repeated single hops (assignment, argument to parameter, return). Each hop draws candidates mechanically, so it can be checked hop by hop.
- **When answers are computed:** mechanical steps are evaluated on demand and cached. Value flow and the fidelity sample are precomputed for every touched symbol, before any writer runs. A value-flow query anchored on a symbol outside that table, for example a caller or binding the writer found with an earlier query, is answered on demand by the same single-hop procedure. Its answer is cached and flagged as on demand. Fidelity is sampled at two points, both before any reviewer outcome is unblinded. The first, before writers run, draws from the precomputed table. The second, after all writers in a phase have run, draws a seeded sample of up to 20 on-demand queries per step from the writers' actual query logs, all of them when there are fewer, with the same adjudication. A step with at least 10 on-demand queries must meet the precision, recall and stability bars on them. The decisive-query requirement applies only to the first sample, so an exploratory step isn't judged on whether writers happened to query near a known defect. A step with fewer is judged on the first sample alone, and the readout reports its on-demand count and results without a gate. Both samples are reported separately.
- **Scope:** a touched symbol is one whose definition the diff changes, or one referenced in a changed line. Symbols defined outside the workspace are excluded by rule; nothing is cut by fan-out.
- **Freezing the definition:** before freezing it, report on development data the share of bugs whose decisive row the table contains.

**Fidelity gate** (per step the engine serves, documented and added alike, since R0 and R both serve simulated rows for documented steps; on at least 40 gold queries drawn from the potential table, settled before any reviewer outcome is unblinded). The sample is stratified. The decisive stratum holds every development query whose scope holds a census decisive row for that step. The random stratum holds at least 20 other queries drawn at random from the potential table, even when the decisive stratum alone reaches 40. Precision and recall are reported per stratum. The random stratum must always meet the bars, and so must the decisive stratum when it is non-empty. A documented step is never removed, whatever its fidelity: R0 and R serve it as is, and the readout reports it at its measured precision and recall. Only added steps can be removed. An added step needs at least 10 decisive queries in its sample, or the decisive-row recall gap is undefined and the step fails the gate. A documented step with fewer than 10 must still meet the precision, recall and stability bars; its gap is reported as not estimable. Documented steps also use real Bifrost as one more mechanical candidate source:
- **Gold set:** built by pooling the engine's rows, a second-family model asked to enumerate, and the mechanical superset, with every candidate adjudicated. For sampled queries whose scope includes a census decisive fact, those decisive rows are added to the gold set even when every enumerator missed them. They are never shown to the engine, so a step that misses the relations it exists to supply can't pass.
- **Accuracy:** row precision at least 95% and recall at least 90%, with lower 95% bounds (bootstrap over queries) of 90% and 80%.
- **Stability:** re-asking a sample without the cache returns the same rows at Jaccard 0.9 or better.
- **Prescience:** decisive-row recall within 10 points of other-row recall. The gap uses only rows some enumerator found (engine, second model or mechanical source), so both sides share the same coverage. Census decisive rows that every enumerator missed count in the decisive stratum's recall bar, but not in the gap. Their count is reported as a shared blind spot. The pilot can only bound this gap to about ±20, which the readout says.
- **On failure:** on development data (the pilot), a failing step is removed before the freeze. After the freeze the menu doesn't change: test-repo fidelity only qualifies the readout, which reports the step at its measured recall. Decisive-row recall on test bugs never feeds back into the menu.
- **Test repos:** measure fidelity on each test repo too, before any reviewer outcome, with about 10 random gold queries per step per repo. Add a decisive stratum per step, frozen before reviewer outcomes exist: every test query whose scope holds a census decisive row for that step, pooled across test repos. The decisive-versus-other recall gap on test comes from that stratum. A failing repo is reported at its measured recall, not dropped.
- **Realistic recall:** ask Bifrost's query-surface owner what recall each step could really reach, per mechanical candidate and per value-flow hop, the units D drops. D's delivered recall is verified on the test cohort, at the same units, from the test fidelity sample, before any reviewer outcome. The readout reports that delivered recall beside D − G. If the engine's own recall at a unit is already below the owner's figure, D can't reach it by dropping, so D isn't run for that step and the readout says so. D is always calibrated to the recall it actually delivers, not just told a retention rate. R's engine already misses some candidates and hops, so D's retention per unit is the owner's recall divided by the engine's measured recall at that unit against the gold set, capped at 1. If the owner can give only recall of returned rows, D's per-hop rate is set so its measured returned-row recall on the pilot matches that figure. If returned-row recall is about 75% or less, add arm D below.

**Arms.** All writers are Sol/high; all arms run in the same window on the same image (`driver --same-image`), interleaved per diff. Every writer and the H helper get the reviewers' isolation, as in `PLAN.md`'s blind brief: a checkout at the introducing commit with no later history, a Podman target, no network, memory, GitHub, builds or helper agents beyond the arm's own, and no corpus records. So no writer can read the fix.
- **N:** no brief.
- **G:** grep writer. It gets the same step list in prose, so the contrast is the answers, not the checklist.
- **R:** mocked-RQL writer, which keeps grep and the list.
- **R0:** the same mocked engine with today's documented steps only (no added steps), keeping grep and the list. R − R0 is the added steps' own contribution, and R0 − G is what complete answers from today's steps add. If no added step survives the pilot fidelity gate, R and R0 offer the same language and answers. R0 is then dropped from the test, R serves the documented steps alone, and the readout records that no added step reached test, with no added-step recommendation. R − G then plays R0 − G's role in the documented-step rule below.
- **H:** compute-matched. A grep writer that may ask a helper free-form questions. The helper has the same model as the answer engine and sees the post-change tree. Unlike the engine, it can also receive whatever the writer puts in a question, including diff text. H is therefore the practical alternative product (a writer with model helpers as it would work today), not an evidence-matched control. Its questions are logged, and the readout reports R − H separately on diffs where no question carried diff text (descriptive). Its token budget equals all the engine model tokens spent answering R's queries on that diff, counted once per diff. That includes precomputed hops and classifications behind those answers, and rejected candidates, rejected hops and other work that produced no rows. A costly empty answer is still information R received. Matching on tokens, not call counts, matters because one RQL call can be a cached lookup or many classification and hop calls. Calls and tokens are reported for both arms.
- **D (conditional):** R with recall degraded inside the engine, not on its final answers. The drop unit is the one the owner's estimate describes. For a mechanical step, each candidate row is kept independently with the step's calibrated retention (see Realistic recall: the owner's recall divided by the engine's measured recall at that unit). For value flow, each hop is one unit (its edge together with the candidate it lands on), kept once with the per-hop calibrated retention, never twice. The delivered recall then matches the owner's: with 75% per hop, a two-hop path survives about 56% of the time, as it would in a real engine. Dropped elements are drawn once per diff and seeded, so repeated queries agree.

**Leak audit.** Each brief's exact text, bound to its hash, gets the blind `judge/SPEC.md` check (one Opus/high) as if it were a review output. Briefs are not rewritten: a blind writer that states the defect from accurate rows is the product working. The readout reports, per arm, the share of briefs that state the defect. A secondary R − G excluding diffs where any arm's brief states it is descriptive only. That exclusion conditions on an outcome of the treatments, so it describes a selected subset and can't cleanly separate writer-found defects from reviewer reasoning.

**Recovery from a location.** Grouping writer sessions by what they happened to query is confounded: a writer can find a fact by grep and then query its location, and the groups differ in difficulty. So the pilot adds controlled conditions on the same development diffs, built from the census's decisive facts. In every condition, decisive facts inside the diff, and facts outside the diff whose cited sites the diff already shows (for example a third-party contract pinned to a changed call), are stated as text, so all conditions get the same cues and the same facts the location arms can't point at; the conditions differ only in how the facts outside the diff are delivered, and recovery is scored on those outside facts that cite at least one site outside the diff. Those facts with no outside site are stated in every condition and left out of recovery scoring, rather than counted as misses in the location arms.
- Fact level. O-fact gives reviewers a brief stating the outside facts. W-fact gives a blind Sol writer the same facts as its only extra input, without RQL access.
- Ceiling. O-loc gives reviewers only the outside facts' own cited sites that lie outside the diff (the census `sites`, as `path:line` at the introducing commit), with no fact text; a cited line the diff already shows is left out, so the location arms highlight no diff line the baselines don't. W-loc gives the writer the same sites. These use the census's knowledge of which facts decide the bug, so they bound what any locator could deliver.
- Blind, realistic. R0-loc and R-loc are arms R0's and R's blind query workflows with the same writer, prompt and engine, except that every returned row is reduced to its source locations: every `path` and line span the row carries (for example both the reaching definition and the use of a `flow-relations-of` row), with any snippet, signature or value removed. R0-loc against R0 compares location-only rows with full rows for documented steps, and R-loc against R does the same for the whole menu, documented and added steps together, in the same blind workflow: the deployment choice between a locator tool and fact rows.
- Baselines. O-base gives reviewers a brief stating only the common text every O condition carries (the in-diff facts and the outside facts with no outside site); N, the no-brief arm, keeps its own role as the baseline-miss measure and is reported for reference only. W-base is the writers' baseline: the same writer, prompt and tools, given the same common text that W-loc and W-fact also receive (the in-diff facts and the outside facts with no outside site), and nothing else. R0, R0-loc, R and R-loc writers are blind and receive no census cues at all, not even the in-diff facts, so each of their contrasts holds cues equal by using one workflow.
Reviewers compare O-fact, O-loc and O-base by catch and by per-fact recovery: the judge records, for each outside decisive fact, whether the reviewer's output identifies it, so a catch through another route isn't counted as recovering the supplied fact. Writers compare W-fact, W-loc, W-base, R0-loc, R0, R-loc and R by per-fact containment of the outside facts; the R0-loc, R0, R-loc and R briefs also go to the pilot reviewers, so those two deployment contrasts are compared by reviewer catch as well, and R0-loc is also compared per fact with G (the same writer and checklist with grep alone), so the readout shows whether realistically returned locations add recovery beyond grep. For R0-loc, R0, R-loc and R, the answer-engine log also shows, per decisive fact, whether the blind session's own returned spans included the fact's outside sites, with the same all, some or none coverage as the census locator queries below, so a miss is split into all-received-but-not-recovered, partly received, and never received. As a further descriptive measure of what RQL can reach, each decisive fact's census `locator_query` is run at the introducing commit, and the readout reports whether its returned spans (a declaration counts for every line it spans) cover all, some or none of the fact's sites outside the diff. R0-loc against R0 decides between locators and fact rows for documented steps, and R-loc against R for the whole menu (it strips documented rows too, so it doesn't isolate the added steps; the pilot's sample is too small to split further), read with O-loc and W-loc as the ceiling a locator could reach and O-fact and W-fact as the value of the facts themselves. Decision margin, set before the pilot: each deployment contrast (R0-loc against R0, R-loc against R) is read as a paired difference in per-fact containment and in reviewer catch, with a 95% interval over diffs. Locations count as sufficient only if both intervals exclude a loss of 10 points or more and the location arm's per-fact containment also exceeds its matched baseline (G, the same writer and checklist with grep alone) with a 95% interval excluding zero, so two arms that both recover nothing can't pass; full rows count as needed only if the containment interval lies wholly below a 10-point loss. Anything else is inconclusive, and the test phase then keeps both the locator and full-row arms rather than choosing. This recovery design is frozen at this revision for the pilot.

**Containment.** One blind Opus judge decides per brief whether it contains the decisive fact (any minimal set), and records for each census decisive fact separately whether the brief contains it, so recovery can be scored against the fact whose location was delivered. Every diff where R's and G's containment differ is hand-checked. R's containment is read only if R actually queried the engine (Terra never called the tool in the Oz run); this rule applies to R's own readout alone. Every recovery contrast, including R-loc against R and R0-loc against R0, scores both of its arms on their full paired pilot sample, so no contrast selects sessions by behavior after assignment. Prompt fixes are allowed in the pilot and frozen before test.
- **Pilot:** containment is reported but gates nothing for the primary contrasts, for the same reason as on test. Its one use as a gate is the locator decision in Recovery from a location, which decides only whether the locator arms join the test phase. The one pilot stop is mechanical: if R doesn't query the engine, fix the prompt in the pilot before going on.
- **Test:** containment is reported but gates nothing, and reviewers run for every arm on the fixed test sample. R can match G on containment yet still lift catch, for example by giving a concrete value or call path, so a containment bound can't rule out the +10 catch effect.
- **Arms N and G** need their reviewers for the census ranking among baseline misses, the contamination measure and G − N. Every arm's reviewers run in both phases.

**Reviewers and judging.**
- Terra/high reviewers. Each brief arm gets 2 briefs per diff with 2 reviewers per brief. N gets 4 reviewers per diff.
- One Opus/high judge per output, plus a hand check of every output. Both are blind to arm, as in `judge/SPEC.md`: outputs carry opaque IDs, come in mixed batches across arms, and arrive without the setup, brief or arm name. The hand check covers caught, partial and missed outputs alike. It records every relation defect the review matched, by defect ID, and its labels are final. No miss is left unchecked, so the estimate needs no sampling correction. It's the pre-registered alternative to a second judge, at about one assessor call per output.
- Harm controls: the non-relation census bugs and the existing ordinary-diff controls, for R against G (retention of confirmed findings), plus brief size per arm.

## Pilot, then test

**Pilot (development only):** mjolnir and bifrost-dev. Its outputs:
- simulator fidelity per step;
- touched-symbol coverage;
- cost and latency per query;
- variance components (repo, diff, brief, reviewer);
- the recovery-from-a-location result: O-loc against O-fact and O-base for reviewers, by catch and per-fact recovery; R0-loc against R0, R-loc against R, and W-loc and W-fact against W-base for writers; and per-fact locator coverage (see Recovery from a location).

These set the test-phase sample. Pilot effects are development data and are never pooled into the reading.

**Test:** the test repos, with arms N, G, R0, R and H (and D if triggered); these full-row arms run in every case, because the primary contrasts (R − G and the helper comparison) need them. R0-loc and R-loc are added when the pilot's locator decision is inconclusive, so the test can settle it. When the pilot finds locations sufficient or full rows needed, the locator arms aren't run on test, and the pilot result stands as the build recommendation.

## Reading

- **Primary:** R − G catch rate on relation diffs, using the hand-checked labels. Take the paired difference per diff, average within each repo, and put a two-sided 95% t interval over repo means (repos − 1 degrees of freedom, equal weights). This one interval governs every decision band in the plan. The same construction applies to R − R0, R0 − G and R − H.
- **Sensitivity checks:**
  - a cluster bootstrap;
  - a mixed logistic model with a repo intercept, a repo arm slope and a diff intercept;
  - the after-cutoff subset.
- **Also reported:** per-repo effects, the between-repo SD and a prediction interval for a new repo selected the same way. The repos were chosen for expected relation-bug yield among those whose index measured under the cap, with indexing hazards excluded, so neither the interval nor the prediction interval covers Rust projects the screen excludes.

Decision bands on R − G, which decide whether complete RQL is worth building for review (minimum effect set by Jonathan, 2026-11-18):
- **Don't build for review:** upper bound below +10. This takes precedence.
- **Build the features:** estimate at least +10 and lower bound above 0.
- **Partial:** lower bound above 0, estimate below +10, and upper bound at least +10.
- **Inconclusive:** anything else, including too few qualifying repos. A band can authorize engine work only with at least 8 qualifying repos (the cohort the stopping analysis started from). With fewer, the reading is Inconclusive whatever the interval, and per-repo effects are reported descriptively.

Fidelity on test governs credit: a Build or Partial reading of R − G, R − R0 or R0 − G recommends engine work only if every step R (or R0) serves passes the fidelity gate on the pooled test repos, decisive-versus-other recall gap included where it's estimable (at least 10 decisive queries pooled across test repos). A served step whose gap isn't estimable must still pass precision, recall and stability. It doesn't block a recommendation, but the readout flags it. Otherwise the contrast is reported as the effect of the answers actually served, at their measured fidelity, and recommends nothing.

Precedence for the engine decision: the helper comparison below can override R − G. If the R − H readout is "helper wins", the helper writer catches materially more bugs, and RQL isn't built for review, however cheap it might be. If it reads "equivalent", a Build or Partial R − G doesn't by itself justify engine work. The decision becomes a cost comparison: build only if real RQL can deliver the same rows at lower cost and latency than the helper's measured tokens and time per diff. Otherwise, R − G governs.

Which features to build, when R − G reads Build or Partial and the helper readout doesn't override it (same repo-level t interval):
- **Added steps:** if the lower bound of R − R0 is above 0, the added steps as a bundle are worth building. The study doesn't attribute that lift to individual steps. Build order comes from descriptive evidence: each step's share of the rows in briefs whose reviewers caught the bug, and the census rankings. As each step is built, it's measured on its own (milestone 5 adds and measures templates one at a time), and a step that adds nothing is dropped.
- **Today's steps:** if the lower bound of R0 − G is above 0 and every documented step served passed the fidelity gate, complete answers to today's steps carry lift, and their completeness and latency are worth engine work. This can hold alongside the added steps. If any served documented step failed the gate, R0 − G is reported as the effect of the answers actually served, at their measured fidelity, and supports no engine recommendation.
- **Unresolved:** a contrast whose interval includes 0 is reported as unresolved. It is never read as showing that part contributed nothing.

Also reported:
- **H against R** (paired R − H, same repo-level t interval):
  - **Upper bound below −5:** the helper writer beats RQL. The useful product today is that writer, and RQL's rows don't earn their cost for review.
  - **Interval within −5 to +5:** a writer with model helpers matches RQL to within 5 points. The useful product today is that writer, and Bifrost's case rests on cost, latency and completeness. If the lower bound is also above 0, the readout reports a real but small RQL edge, which counts as practically equivalent.
  - **Lower bound above 0 and upper bound at least +5:** RQL's structured rows add value over equal helper compute.
  - **Otherwise:** unresolved.
- **D − G** (when D runs; paired, same governing interval): a sensitivity check on random recall loss, reported but vetoing nothing. A real engine's misses are systematic, not random: whole site classes such as macro expansions, cfg-gated code or trait dispatch. Random drops can match its aggregate recall while keeping a very different share of decisive rows, so D can neither confirm nor rule out a feature at realistic recall. Systematic-miss risk is reported instead from the candidate source tags: for each step, the share of decisive rows only rust-analyzer or grep found, which today's Bifrost misses. The paired R − D contrast is reported alongside.
- **G − N:** the effect of the checklist-assisted grep writer over no brief. G gets the new step list in prose, which the shipped writer's prompt (`WRITER.md`) doesn't have, so this isn't a measure of the shipped writer itself.

## Cost and quota (estimates, refined by the pilot)

- **Census:** from the bifrost-dev records (scouting): tracing cost about $0.16 per attempt, and 263 attempts yielded 30 accepted bugs, 17 of them relation bugs. That's about 15 attempts per admitted relation diff, before the screen's blame pre-filter improves it. 12 repos at 25 relation diffs is up to about 4,600 attempts (about $750), plus two labellers per admitted bug (about $0.12 each, up to about 530 admitted bugs counting local ones): about $800–1,000 in all, plus development. Tracing stops sooner in repos whose supply runs out.
- **Pilot:** about $350–500 in API-equivalent terms. That covers 35 relation diffs:
  - about 700 Terra reviewer sessions;
  - about 280 Sol writer sessions;
  - about 700 Opus judge calls and 700 Opus hand checks, one each per reviewer output;
  - the simulator and the gold set.
- **Test:** about 7 times the pilot for 12 repos.
- **Indexing:** Bifrost and rust-analyzer compute for each bug's introducing commit, reusing incremental indexes within a repo. Every Bifrost or rust-analyzer run in this study, including the answer engine's candidate generation at each introducing revision, runs only on EC2 hosts, never the user's workstation. Each runs in its own systemd scope with a MemoryMax cap and MemorySwapMax=0, as `measure_index.py` does, and records its whole-tree peak. A cap hit is a recorded failure for that revision. A safe measurement at the two pinned commits doesn't make older revisions safe. Clones come from each repo's origin at pinned commits.
- **Quota:** Sol and Terra on codex; Opus on the Claude profiles the coordinator allots (load-balanced by `mj new --model opus`; claude7's week ran out on 2026-11-19, and the methodology needs only the Opus family at high effort). Keep every profile used above 25% of its week, checked before each launch, and don't use codex4.
