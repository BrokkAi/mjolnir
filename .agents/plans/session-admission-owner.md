# One owner decides which work may use a session's worker (#1562, #1564)

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. It is maintained in accordance with `.agents/PLANS.md` at the repository root.


## Purpose / Big Picture

The daemon runs many kinds of work against one session's live worker: a person's Move, close, suspend, resume or restart; automatic recovery copies, worker upgrades, credential syncs, quota recovery and delegation result delivery. Today four independent per-session gates decide whether each may run, and none of them knows what the others are doing, so one kind of work can starve or block another.

Two failures on 2026-11-17 show it. In #1564 a renewed Claude login (renewal revokes the previous access token) never reached session 85e2d8a9 because its recovery copies, each about ten minutes long, ran back to back and held the only background slot; the credential sync was turned away every minute for half an hour and every turn failed with "Authentication required". In #1562 a person's manual `mj move --profile codex4` for session 70506548 failed at once with "session already has a lifecycle operation" because some other operation held the session actor's relay lease; meanwhile automatic quota recovery retried every 15 to 50 seconds for 15 minutes under a 15-second cap that counted queue time, and finally moved the session to a profile the person had not asked for.

After this change one owner per session decides. A person's lifecycle operation announces itself first, stops automatic work that can be safely dropped, waits for the rest and names it while waiting, and then runs; it never fails "busy". Automatic work tries admission, is refused with the name of what holds the session, and retries on a state change or with backoff. Kinds of work that do not conflict, such as a credential sync and a recovery copy's transfer, run together. The relay lease is handed out by the same owner, so the actor never has to refuse a duplicate.

How to see it working: in an isolated instance, start a long recovery copy (or hold one in a test), renew a login, and observe the login pushed while the copy runs; with a delegation delivery or quota recovery in flight, run `mj move` and observe "Waiting for <named operation>" followed by the Move completing, not a refusal.

## Surprises & Discoveries

- Observation (2026-11-17, Milestone 3 second review): `request_review` returns after registering reviewers while its ReviewSlot retains a review reservation. Such a reservation must admit DelegationDelivery even outside Move's drain, or the acceptance reply and other MCP replies cannot reach the waiting harness. Foreground reservations remain exclusive except their explicitly scoped drain.

- Observation (2026-11-17, Milestone 3 second review): `retire_legacy_wait` was another deleter of effect rows besides acknowledgement: it transferred old report ownership to the mailbox, deleted the effect, then the API built an in-memory compatibility reply. The new delivery reload mistook that deletion for prior acknowledgement and skipped the reply. Conversion now persists and returns the compatibility result in the same transaction as report transfer, leaving ordinary acknowledgement as the result's deletion point.

- Observation (2026-11-17, Milestone 3 first review test): the queue observer initially publishes an unknown/connecting error with an empty request list. The inline prototype regression could finish before its real pending request was observed once the durable effect result became ready. Drain now waits on the observer's authoritative unknown state instead of treating it as an empty queue, and names the synchronization error while waiting. This is the same drain completion decision, not another admission predicate.

- Observation (2026-11-17, Milestone 3 first review follow-up): the preferred inline-delivery prototype can race `SubagentDispatch::Phase::Recovery`/`Executing`. A recovery executor may have been scheduled before Move reads a stored result but not yet run `ApiBackend::execute_subagent_tool_durable`'s initial load. If Move then acknowledges and deletes that result, the recovery executor sees no effect row and prepares execution again. Fixing this would require coordination with the dispatch loop's in-flight per-request state. The parent's explicitly approved alternate is therefore used: the same foreground reservation temporarily admits background delivery and yields its own ability to lease; the existing dispatch state machine remains the sole per-request execution/delivery owner. No inline acknowledgement remains in Move.

- Observation (2026-11-17, Milestone 3 first review): in-place Move closes mutating sub-agent admission, returns its relay lease and waits for accepted mutations and their durable effects to drain (`move_session.rs::drain_subagent_mutations`). Those requests remain in the worker queue until delegation result delivery completes them. The new unconditional foreground reservation exclusion in `RecoveryGate::try_start` prevents that delivery, so Move waits on work it forbids. The review finding is accepted and requires a parent ruling on an owner-controlled foreground drain transition. Merely permitting delivery would also expose the drain's current `handle.sync_now()` calls to the actor's normal leased-sync refusal; the correction must account for both admission and observation while delivery leases run.

- Observation (2026-11-17, Milestone 3 implementation): an accepted lease reply previously carried a raw `(lease_id, connection)`. Dropping the receiver after actor send but before handle receive dropped the connection without sending the return, stranding actor ownership and, with owner-backed lease lifetime, its admission. The reply now carries `ManagedSessionLease` itself, whose drop returns the lease; the existing cancelled-request regression covers both sides of send.

- Observation (2026-11-17, Milestone 3 investigation): after `ReleaseAfterLatch`, a failed archive transfer can call `ControllerRelayLease::cancel_abandoned_barrier`, which currently reacquires a fresh actor lease when the original lease has been returned (`checkpoint/lease.rs:100-109`). Once the copy narrows to transferring, delegation delivery is deliberately admissible beside it, so the transferring capability cannot authorize this fresh lease. Narrowing alone does not cover every existing lease request. The parent resolved this with the async transferring-to-abandoning transition recorded in the Decision Log.
  Evidence: `latched.rs:528-529` returns the original connection; `lease.rs:233` uses `cancel_abandoned_barrier` on failure. The actor gives queued lease returns priority over commands (`actor.rs:153-159`), so normal release ordering already has an explicit guarantee and need not gain another queue.

- Observation (2026-11-17, eighth review): using foreground-style reservation-before-wait for reviews blocked credential sync beside an existing recovery copy, even though review admission deliberately leaves the copy running. Preserve background compatibility during a review's wait by installing its reservation only when background holders are empty, under the same owner lock as that idleness decision.

- Observation (2026-11-17, seventh review): the new bounded destroy preemption branch bypassed the ordinary queue's drain notification. An unaccepted destroy therefore kept its outer client and destroy admissions until preemption timed out, even when the active lifecycle had released its own hold for resumable preparation. Race that existing bounded wait against the same authoritative daemon drain; refusal drops the pending destroy and returns the existing retry-safe wire disposition.

- Observation (2026-11-17, sixth review): personal destroy preempted the active lifecycle before registering its queue intent. An earlier queued Resume could therefore become active in that gap, and the ordinary personal-wait policy then lost destroy's existing bounded preemption behavior. The fix registers a priority destroy/child-stop intent in the same registry queue before selecting the active operation for preemption under its owner lock. The bounded wait uses that selected operation's identity; ordinary queued requests cannot take ownership before destroy admission.

- Observation: releasing a running lifecycle's resumable-work hold does not release a different queued request's outer client-request admission. Queue waits therefore must observe draining and return explicitly unaccepted instead of waiting for the running lifecycle's result indefinitely through handoff.
  Evidence: reviewer 1 of `5b46f3845`; `queued_lifecycle_requests_release_client_admission_for_handoff_and_stop` drives authenticated TCP StartSessionLifecycle while a personal container upgrade holds its session but has released daemon admission.   Evidence: reviewer 1 of `f9e68d823`; the queued-Resume regression now returns DeferredCleanup from the preceding Suspend and uses the existing recorded-command Podman fixture helper to verify exact container removal and a cleared durable locator before Resume reaches capacity admission.

  Evidence: all three independent reviewers of `352a87453` identified this regression. The owner now records compatible review/foreground reservation kinds, and the resumable-lifecycle regression holds a review across foreground work to prove it cannot block entry.

  Evidence: reviewer 1 of `352a87453`; regression `queued_resume_rechecks_state_after_suspend_before_reserving_capacity` queues before the store transition, then verifies the resumed operation reaches fresh capacity admission instead of returning an already-running success.

Its existing resumable-lifecycle test assumed that hold was still present on entry to the work closure, and blocked on a signal after that assertion failed. The expectation now checks that Unpark has already released it; other lifecycle kinds retain the hold until their explicit resumable-work hook.
  Evidence: initial focused run `resumable_lifecycles_release_admission_and_reacquire_named_control` assertion at the work closure; the isolated child was stopped after the failed assertion left its waiter blocked. Log: `.mj/agents/906ef37490dee3aff0bc1c895b467698/lifecycle-tests.log`.

  Evidence: initial focused run `restart_intent_checks_cancellation_and_records_its_sealed_checkpoint` timed out waiting for the cancel flag of a personal Restart. Same focused-run log.

- Observation: lifecycle admission methods currently return synchronously, and recovery/startup helpers call them synchronously too. Waiting on an existing lifecycle requires converting the admission entry points and those callers to async methods. The registry now records arrival tickets under its existing owner lock; a dropped waiting future removes its ticket. The gate has no intent queue.
  Evidence: `start_or_join_lifecycle_controlled`, `admit_lifecycle_mode`, `recover_moves`, `recover_restarts`, and `start_create_lifecycle` previously returned a result immediately.

- Observation: the existing review admission deliberately granted a reservation at its deadline even while background work remained. This contradicts non-overlapping foreground admission.
  Evidence: `reserve_when_idle` previously admitted when `Instant::now() >= deadline` even if `state.busy` contained the session.

- Observation: renewing a Claude login revokes the old access token at once (85e2 held a token whose `expiresAt` was 07:22 and was refused at 03:44). So every session must receive the push before its next request.

## Decision Log

- Decision (2026-11-17, Milestone 3 second review): review reservations admit DelegationDelivery but continue excluding other background kinds. Legacy-wait conversion retains a canonical compatibility result until worker acknowledgement, returning it from the database transaction instead of reconstructing a reply after deleting its row.
  Rationale: a review is long-lived worker work whose acceptance must reach the primary immediately. Durable wait conversion preserves both transferred reports and retryable reply ownership. This writes the same existing result JSON shape and `result` phase already used for new legacy-wait requests; no schema, protocol or persisted format change is introduced.

- Decision (2026-11-17, Milestone 3 first review alternate authorized by parent): a scoped `ForegroundDelegationDrain` is a phase of the same foreground identity. It permits only DelegationDelivery while preventing the foreground from leasing. Closing the scope restores exclusive foreground admission, cancels admitted delivery and makes foreground reacquisition wait for every delivery holder and physical lease return. Guard drop closes the phase on cancellation/unwind. Leased Sync refusals retain `RelayJobDeferred` as an internal typed cause, so the existing drain polling waits on that condition while propagating real failures; wire formatting is unchanged.
  Rationale: the dispatcher owns Recovery/Executing/Delivering state. Keeping its execution and acknowledgement together avoids Move deleting a durable result before a scheduled recovery reads it. The prototype established why the parent's preferred inline delivery cannot be adopted without adding per-request coordination. Delivery keeps its existing retry/backoff, and ordinary foreground/background exclusion remains unchanged outside the scoped drain.

- Decision (2026-11-17, Milestone 3 implementation): retain the admission in an owner-issued relay guard until the actor applies the return, and send a `ManagedSessionLease` guard across the reply channel rather than raw connection parts. Reacquisition waits on the same owner's publication until a prior return is applied. No queue, protocol or persisted contract is added.
  Rationale: the actor's return-channel priority protects command ordering, but cannot by itself preserve admission or release an unread successful reply. Ownership must cross cancellation boundaries with the connection.

- Decision (2026-11-17, Milestone 3 parent ruling): use the owner-controlled graph Capturing → Transferring → Abandoning. The first transition is synchronous narrow; the second is asynchronous, cancels delegation delivery and waits for its return before granting the cleanup lease, even while a foreground reservation waits. Abandoning remains compatible with credential sync. Thread admissions explicitly through registry closures, blocking recovery work and all lease users, including WorkerReplacement and workspace upload; never obtain them from ambient state.
  Rationale: cleanup must disconnect an abandoned barrier without advancing its recovery floor. A transition of the same attempt avoids a separate cleanup admission and a deadlock against its own transferring holder. Every lease taker must present the sole owner's capability.

- Decision (2026-11-17, Milestone 3 start): a relay lease continues to make the actor refuse `run_on_connection` jobs with `RelayJobDeferred`; do not retain jobs in the actor. Record a credential sync deferred by a lease with the session owner, and use the lease-return state transition to wake reconciliation for that session immediately instead of waiting for `SYNC_INTERVAL`.
  Rationale: the profile reconciliation pass is sequential, and retaining a job behind a Move lease would stall unrelated sessions for minutes. The owner is the one place that can coordinate lease lifetime and the wake without adding an independent admission predicate.

- Decision (2026-11-17, eighth review): foreground admission reserves before cancelling/waiting; review admission reserves only when background work is idle. Both transitions remain in the same RecoveryGate owner method and mutex. A waiting review may be overtaken by compatible background work; its existing caller-owned admission deadline still bounds the wait.
  Rationale: a non-preempting waiter must not prevent the credential update needed by background work it deliberately permits to continue. Once the review is admitted, its reservation excludes all new background work as before.

- Decision (2026-11-17, seventh review): all unaccepted lifecycle waits, including destroy preemption, yield to the existing daemon gate's drain publication. The bounded preemption future is retained until completion or draining, preserving its timeout across the wait; draining drops that wait and its queue intent without admitting destruction.
  Rationale: bounded preemption does not make an unaccepted request daemon-owned work that may delay replacement. This uses the same gate notification and refusal as ordinary queue waits and retains accepted destroy semantics.

- Decision (2026-11-17, sixth review): retain ForceDestroy and accepted parent-owned StopSubagent as explicit priority intents in the existing lifecycle queue. Select cancellation and its result watch under the registry owner; wait using the existing preemption budget, then admit under the same owner's queue ordering. Remove the pre-queue preemption call. A timeout still refuses destruction and removes its intent, and committed teardown remains uncancellable. Pin late timeout cancellation to the selected operation ID.
  Rationale: FIFO personal waiting is for ordinary operations, while destroy is the existing escape hatch. Keeping this exception inside registry admission prevents queue turnover from changing that policy; it introduces no additional gate, timeout, or persisted contract.

- Decision: queued, unaccepted lifecycle calls yield when the daemon's existing handoff gate begins draining. The gate publishes that transition through a notification; the queue returns the existing `daemon_handoff` refusal and removes its ticket. Selection from a queue also uses draining-aware handoff admission, including the existing bounded destroy registration, to close the completion-versus-drain race. Stop begins the same drain before shutdown; an already-stopped request remains a no-op.
  Rationale: review of `5b46f3845` found that a queued StartSessionLifecycle kept its outer client-request hold while the running personal upgrade was doing resumable image preparation. The daemon could not close admission to cancel/resume that preparation. The existing gate remains the only owner of draining; notification adds no parallel decision state or polling. Only unaccepted receipt-start refusals become the existing UpgradePending wire reply, so clients retry their original request/selection without replaying accepted mutations.
  Date/Author: 2026-11-17 / Milestone 2 fifth review correction.

- Decision: resolve Resume's deferred target cleanup inside its admitted lifecycle, from the same fresh durable record that determines whether it is already running. A stopped record retaining a target is cleaned through `Controller::cleanup_stopped_target`, then the controller is reloaded before capacity/provisioning. Do not start or wait for a second cleanup lifecycle while Resume owns the session.
  Rationale: review of `f9e68d823` found the earlier cleanup check could run while Suspend was still Running. Suspend could then publish DeferredCleanup while the queued Resume prevented the automatic cleanup lifecycle from starting, leaving a stopped Podman container with the name Resume needed. The existing idempotent cleanup operation now belongs to the admitted Resume.

## Context and Orientation

The daemon (`mj daemon-run`, crate `brokk-mj-controller`, directory `mj-controller/`) is the control plane; one worker process per session (crate `mj-worker`) runs the coding agent. The daemon talks to a worker over a "relay" connection. Each live session has a "session actor" (`mj-controller/src/session_manager/actor.rs`), a task that owns the session's relay connection, runs queued relay jobs on it, and can lend the connection out exclusively ("lease") to one caller at a time (`ActorCommand::Lease` near line 1115; `ActorLifecycle` in `mj-controller/src/session_manager/actor_types.rs` holds `active_lease: Option<u64>`). A second lease request while one is active is refused with "session already has a lifecycle operation". Callers obtain a lease with `ManagedSessionHandle::lease_connection` or `lease_idle_connection` (`mj-controller/src/session_manager/handle.rs` lines 308 and 313).

The four per-session admission mechanisms today:

`RecoveryGate` (`mj-controller/src/recovery_gate.rs`) is created once per daemon runtime and shared by the recovery coordinator (`mj-controller/src/recovery.rs`, starts recovery copies), the worker upgrade coordinator (`mj-controller/src/worker_upgrade.rs`, replaces workers with the current build), and the credential sync coordinator (`mj-controller/src/worker_client/credential_sync.rs`, function `admitted`, pushes logins, AWS credentials, GitHub tokens and skills). Background work calls `try_start`, which returns `None` if the session is held or reserved. Foreground lifecycle operations call `reserve_recovery_or_cancel` (`mj-controller/src/pollers/lifecycle.rs` line 132), which reserves, cancels in-flight holders, and polls until they release; callers are in `mj-controller/src/daemon/` (`session_move.rs:670`, `close.rs:41,523`, `resume.rs:99,835`, `restart.rs:263`, `subagent_park.rs:212,308`). A turn review calls `reserve_when_idle` (`mj-controller/src/review_host/environment.rs:425`).

The actor relay lease, described above. Takers: Move (`mj-controller/src/controller/move_session.rs` lines 612, 636, 816, 2276), close recovery (`mj-controller/src/controller/lifecycle.rs:657`), checkpoint capture (`mj-controller/src/controller/checkpoint/barrier.rs`, `relay.rs:135`, `latched.rs`, `workspace_lease.rs`), and delegation result delivery (`mj-controller/src/daemon/delegation.rs:678`, which already retries with backoff).

`WorkerPermit` (`mj-controller/src/worker_lifecycle.rs`) is a process-global per-session slot for mutating worker processes, with a label (`reason`) and task-local nesting so nested calls reuse the permit. Foreground callers `acquire` (wait, with a notice), background callers `try_acquire`.

Move's own ownership map (`move_ownership()` in `move_session.rs` line 32), which records an in-flight Move for command refusal; it is bookkeeping, not admission, and is left alone.

The daemon lifecycle registry (`state.owner().lifecycle`, admitted in `start_or_join_lifecycle_controlled`, `mj-controller/src/daemon/lifecycle.rs` around line 92) holds at most one foreground lifecycle per session (Move, Suspend, Resume, Restart, Park, Unpark, ForceDestroy, UpgradeContainer, ...). An identical request joins the running one; any other request fails in `check_request` (`mj-controller/src/daemon.rs:630`) with "another lifecycle request with different selections is already running" or "another lifecycle operation is already running". This is what a person's Move meets while an automatic quota Move runs.

Quota recovery: the continuation loop (`mj-controller/src/daemon/continuation.rs`, around lines 640 to 790) acts once per worker assessment revision; it resolves a plan (`(env.quota)`) and then calls `quota::schedule` (`mj-controller/src/daemon/continuation/quota.rs` around line 406), which wraps lookup, checks, `SetQuotaRecovery` submit, sync, Move admission (`start_quota_move`) and fallback in `tokio::time::timeout(Duration::from_secs(15), ...)`. `quota::resume` has the same shape. The worker rejects a schedule whose cursor moved (`mj-worker/src/relay/commands.rs` around line 709, "quota recovery evidence is stale").

Daemon handoff admission (`gate.enter_unless_draining` in the continuation loop and `crate::upgrade::is_draining()` in `RecoveryGate::try_start`) is a different, daemon-wide gate for upgrades; its admission policy is preserved, and Milestone 2 adds publication of its existing draining/closed decision so queued unaccepted callers release their client holds. Automatic work keeps refusing while it drains.
