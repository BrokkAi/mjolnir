# Move the AFK repeated-question check and the question locator from Jev to GLiDE

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. It follows `.agents/PLANS.md` (repository root) and must be maintained in accordance with that file. Tracking issue: #1533.

## Purpose / Big Picture

Mjolnir ("mj") uses hosted text classifiers to make small judgments about agent sessions. Two providers exist. Jev is the TypeSafe classifier (model `jev-latest`). GLiDE is the Fastino classifier (model `fastino/GLiDE`). The completed-turn verdict, the sub-agent handback check and the GitHub item classifier already moved to GLiDE, where they measured as well as or better than Jev. Two live classifiers still call Jev:

The AFK repeated-question check. "AFK" (away from keyboard) is a mode in which the person tells mj they are away. While it is on, the first question an agent asks is declined at once with an "operator away" answer, so the agent proceeds on its own judgment. When the same agent asks again, mj must decide whether the new question repeats one already declined (then it is held for the person, because the agent evidently needs them) or is a new decision (then it is declined too). Jev makes that same-or-different call.

The question locator. When the completed-turn verdict decides a turn needs the person's input, and the agent wrote several replies since the person's last message, the locator picks the reply that holds the open question, so the TUI and web viewer open the session scrolled to it instead of at the bottom.

After this change both run on GLiDE through the hosted proxy, each is measured on labeled cases and tuned (question wording, input sizes, decision thresholds) to be at least as accurate as Jev, the AFK check writes a decision log so future production evidence exists, and the dead Jev client code in the worker is removed. The person sees the same behavior: repeated AFK questions wait for them, new ones are declined, and needs-input sessions open at the question.

- Decision: locator acceptance is measured against today's fallback, "open at the bottom", with two rates. Help is the share of cases whose truth is an older reply (not the newest) where the design picks an acceptable reply. Harm is the share of all cases where the design scrolls to a reply outside the acceptable set (this includes any pick when the truth is `none`). The frozen design ships if, on held-out point estimates, its harm is no higher than Jev's and its help is no more than 10 points below Jev's. Pooled accuracy is reported as a secondary number, with a session-clustered bootstrap 95% interval on every paired difference and a statement of the smallest difference the held-out set could detect. Two further baselines are scored everywhere: "always the newest reply" and "always none". Help's denominator is the older-truth cases only (expected 50 to 70 in held-out, from about 15 to 20 sessions, with session-clustered noise near plus or minus 12 to 15 points), so 10 points is about the smallest margin the data can resolve; a pass means "not clearly worse than Jev", not "shown equal", and the report says so. Before choosing a design, check Jev itself on the labels: if Jev's help is low or its harm exceeds its help, report that to the parent first, because then matching Jev is not a useful bar and "always the newest reply" becomes the comparison that matters.
  Rationale: Advisor review (session 91233b0e, 2026-11-13). Only an older-reply pick changes what the person sees, and "always newest" is already right on 101 of 115 fixtures (Jev 81 of 90), so pooled accuracy cannot separate designs and hides whether a loss is help or harm. The session-clustered interval on the paired difference is roughly plus or minus 5 to 7 points at this size, so an interval-bound gate would fail designs equal to Jev; for a feature whose worst error is a harmless scroll, point estimates with reported intervals are proportionate.
  Date/Author: 2026-11-13, parent session.
- Decision: freeze locator design V0 with the argmax rule. V0 is the existing `question_locator.json` instructions with criteria `rK` and `none` as plain strings, keeping the Jev-era budgets (3,000 bytes per reply, 32 replies). On logged tuning cases it scored help 38/40 and harm 14/243, against Jev's 36/40 and 24/243. Only V0 runs as the selected design on held-out. V2 (one yes/no question per reply, threshold 0.7) also runs there with its threshold fixed in advance, but is reported as not selected; a clearly better held-out result for it is recorded for a later revision with fresh labels and does not switch the design. Before the held-out run, the reading of a narrow miss is fixed as follows. The held-out gate is the primary result. The declared secondary analysis is the paired V0-versus-Jev difference on all 379 labeled logged cases, with a session bootstrap. It is defensible because nothing in V0 was fitted, but it is slightly optimistic because V0 was selected among four designs on tuning. A held-out help miss with a pooled tie goes to the user as "inconclusive on held-out, equal overall", not as a failed port. The report splits V0's harm by truth class (newest, older, none).

## Context and Orientation

Terms. The daemon (crate `mj-controller`) is the control plane. A worker (crate `mj-worker`) runs one session's agent. The proxy (`services/jev-proxy`, a TypeScript Cloudflare Worker deployed as `mj-jev-proxy`, public URL `https://mj-jev-proxy.eng-admin-a63.workers.dev`) holds the provider keys and forwards classifier requests. An elicitation is a structured question form an agent sends to the person (type `mj_core::elicitation::ElicitationRequest`, `mj-core/src/elicitation.rs`). The decision log (`mj_core::jev::DecisionLog`, `mj-core/src/jev.rs`) is a per-worker JSON-lines file under `<data dir>/workers/<id>/jev-decisions/decisions.N.jsonl`; each start, update and finish of a decision appends a line with the same `id`, so readers deduplicate by `id` and keep the last line. `[jev] enabled` in the config file is the Privacy switch; when it is off the worker builds no classifier client and neither feature runs (env `MJ_JEV_DISABLED`).

GLiDE request shape. POST `https://api.fastino.ai/v1/systemone` with header `X-API-Key` and body `{"model":"fastino/GLiDE","state":<object>,"questions":<object>,"store":false}`. Each question is `{"type":"choice","instructions":"...","criteria":{"<label>":"<plain description>"}}` (criteria values are plain strings; Jev used `{"what": ...}` objects) or `{"type":"noul",...}` for yes/no. The answer for a choice question has `probabilities` over every label summing to 1 within 0.03; callers use only `probabilities`. The proxy's helper is `glide()` in `services/jev-proxy/src/glide.ts`. A new GLiDE route must be added in `services/jev-proxy/src/index.ts` to the key selection (~456, so it uses `FASTINO_API_KEY`), the body bound (~468, `GLIDE_BODY_BYTES`) and the route table, and must use its own handler because `classify()` chooses Jev questions by state shape.

The AFK check today. `PendingElicitations::refine_question` (`mj-worker/src/acp/operator_away.rs` ~187-286) calls `VerdictClient::same_afk_question(current, previous)` (`mj-worker/src/acp/verdict_client.rs` ~188-300). Evidence per form comes from `question_evidence` (`operator_away.rs` ~46-67): the serialized form without `id`; secret fields lose `default` and gain `"secret": true`. Before sending, secret option strings are replaced by request-local labels (`anonymize_json_strings`) and all strings pass the token redactor with distinct labels for distinct identifiers (`redact_json_strings_distinct`), so equality of values survives redaction. State is `{"current_question": form, "previous_questions": [form, ...]}`. The question is `mj-worker/src/acp/afk_question.json` (one choice `same_question` with labels `same` and `different`). The rule is "same unless different has strictly higher probability". Outcomes: different means decline now ("operator away"); same, any error, or Jev off means hold the question for the person. A state change (person returns, answers, history changes) cancels the in-flight request and reclassifies. Tests in `operator_away.rs` (~432-881) use a fake HTTP classifier and assert the privacy transforms and cancellation.

The locator today. After a completed turn is assessed as needing input (`mj-worker/src/worker_runtime/unix/dispatch.rs` ~358-385), `relay.question_locator_request` (`mj-worker/src/relay/verdict.rs` ~347-367) builds a request with `mj_core::activity::question_locator::build` (`mj-core/src/activity/question_locator.rs` ~62-98): the last 4,096 bytes of the person's latest message and up to 32 newest assistant replies since it, each clipped to a 3,000-byte budget (head two thirds, tail one third), shrunk by 0.8 until the state is at most 60 KiB. With one reply it stores that reply without asking. With two or more it calls `locate_question` (`verdict_client.rs` ~325-400), whose question is one choice `request_reply` with labels `r0..r(n-1)` and `none` (`question_locator.rs` ~104-114, instructions in `mj-core/src/activity/question_locator.json`). The rule is argmax; `none` stores nothing. The answer is stored with `store_question_target` only if the assessment is still current, as `TurnAssessment.question_message` (a stable transcript id such as `agent:<id>`); the TUI and web viewer scroll to it. Every call writes a decision record with `checked = "Which reply contains the open question?"`, `technical.request` (the exact body) and the answer.

Evaluation assets. `mj-core/tests/jev-scenarios/*.json` has 122 fixtures with `outcome.request_message_ids` (acceptable reply ids; 115 have at least two replies after the last user message), with full messages at `evidence.authorization.messages`. `scripts/jev-question-locator-eval.py` rebuilds the locator state from fixtures and asks TypeSafe directly; it is the template for the GLiDE script. Recorded Jev results: 81 of 90 on the 30 W-series fixtures times three repeats; 17 of 18 held-out positives. There is no AFK corpus.

## Plan of Work

All evaluation output goes to `/mnt/optane/tmp/glide-afk-locator-20261113/` (local, private: it contains transcript text). Production text stays on this host except for the classifier calls, which send the same class of data production already sends to Fastino. Labelers are agents that read cases blind (they never see any classifier's answer or another labeler's label) and write one label per case to a file as they go, so work survives interruptions.

Milestone 1 (locator corpus). Write `scripts/glide-question-locator-corpus.py` that reads every worker decision log in the default instance's data directory read-only, keeps records whose `checked` is the locator question, deduplicates by `id`, drops single-reply records, and writes one case per decision with the logged state, Jev's logged answer (and its top probability), session id, time, reply count, and whether any reply was clipped. As of 2026-11-13 this gives about 380 cases in 114 sessions; Jev chose the newest reply in about 66%, an older reply in 27%, `none` in 7%, and ten sessions hold 60% of the cases. Also rebuild the states of the 115 usable fixtures with the current Rust rules (labels from `outcome.request_message_ids`).

Split before any GLiDE call and write the split file. All fixtures go to tuning (Jev's wording was fitted on them). The five sessions that appear in both the fixtures and the logs (about 111 logged cases) also go to tuning. Divide the remaining logged cases by session into tuning and held-out halves, stratified by session size and by Jev's logged answer type (newest, older, none), with a fixed seed, so each side has older-reply and `none` cases.

Label every logged case with two independent blind labelers and adjudicate disagreements with a third. A labeler marks every acceptable reply (a reply that holds a request the person has not yet answered, following `question_locator.json`; several replies can be acceptable when a request repeats), or `none`, or "cannot tell from the clipped text". Mix known fixtures into each labeler's queue without marking them, including the 14 fixtures whose answer is an older reply, and check each labeler's accuracy on them and their share of "newest" answers; earlier cheap labelers judged from the final reply only. Jev baseline: logged cases use Jev's logged answer (one call, as in production); fixtures are re-run through Jev with the existing script three times and the single-run mean is reported, not a majority.

Milestone 2 (locator design). Write `scripts/glide-question-locator-eval.py` (stdlib only, modelled on the Jev script) that sends variants to Fastino directly and reports, per variant and baseline, help, harm, pooled accuracy, results by reply count (2 to 4, 5 to 9, 10 or more), latency and requests per case. Variants on the tuning split: V0, the direct port (same instructions, criteria `rK` as plain strings); V1, criteria rewritten for GLiDE in the categorical style that worked for the handback check; V2, one yes/no (`noul`) question per reply inside a single request with all replies, choosing the newest reply above a threshold; V2b, one request per reply (the person's message plus that one reply), newest first, stopping at the first yes, at most K replies (try K = 4 and 8; Jev's picks fell within the newest four replies in 312 of 352 located cases), which removes the dependence on index labels. For choice designs also fit a `none` margin (choose `none` unless the best reply's probability exceeds it) on logged tuning cases only. Check determinism once on about 20 cases instead of repeating every variant. Run V3 (larger inputs) only if labelers mark a material share of cases "cannot tell from the clipped text": then rebuild those cases' full reply text from the daemon store and test per-reply bytes and reply count separately (the proxy's refusal-driven shrink sets the real budget, since 64 replies at 12,000 bytes exceeds the 256 KiB bound). Freeze one design (question file, budgets, rule) in a `FROZEN/` directory, then run it once on the held-out split and compare with Jev and the two baselines on the same cases.

Milestone 3 (AFK corpus). Size for the error the gate measures: false-different is measured only on "same" pairs, so build at least 100 "same" pairs (0 errors in 100 bounds the rate near 3%; 0 in 25 only near 11%) and at least 50 "different" pairs, of which 20 to 30 are "the repeat plus one new decision", the hard boundary of the wording. Sources: real elicitation forms from the default instance, read-only (start from the daemon store's transcript items for elicitation and question requests; if direct reading of the 16 GB store stalls, copy only the needed tables), paired by session and agent in time order; and constructed pairs built from real forms. Build repeats by replay: give a model the form and the "operator away" answer it received and have it ask again, which is closer to a real repeat than a paraphrase instruction; also include subsets and reorderings. Build "different" pairs from added decisions, changed option sets or constraints, and unrelated questions. Match what production sends: `previous_questions` is the list of every form already declined for that agent (`refine_question`, `mj-worker/src/acp/operator_away.rs` ~217-225), so place the matching form (for "same") among 1 to 5 unrelated earlier forms at varying positions. Apply the production privacy transforms (secret fields, anonymized options, redacted identifiers) to every pair. Real pairs and "repeat plus one new decision" pairs get two blind labels and adjudication; other constructed pairs carry their construction label checked by one labeler. Jev baseline: run the current Jev question once over all pairs.

The new proxy routes are additive; if one misbehaves after deployment, the previous proxy version can be redeployed with `npx wrangler rollback` while workers fall back to their failure behavior (AFK: hold for the person; locator: open at the bottom).
