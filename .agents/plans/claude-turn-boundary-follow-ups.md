# Claude turn boundary, part two: order the decision, settle harness turns on results, let Stop work

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. It follows `.agents/PLANS.md` and must be maintained in accordance with it. ## Purpose / Big Picture

Part one makes a Claude prompt turn end when Claude Code reports the result of the cycle that answered it, instead of when the adapter finally answers `session/prompt`. This plan finishes the job in three ways a user can see.

First, the decision is made in the one place that sees the adapter's notifications in order, so the text of the answer always lands inside the turn it belongs to, and no completion can race the answer's last chunk. Second, a self-started Claude cycle (a "harness turn": Claude Code woke the model because a background subagent, shell, or Monitor finished) also ends at its `result`, not at the adapter's origin marker, which the adapter omits when a cycle has no assistant usage; the known "session stuck Running after a stray chunk" limitation goes away for the common case. Third, pressing Stop while such a cycle runs actually stops it. Today the worker refuses with "the agent is working on its own"; after this change the cycle is interrupted, the session goes idle, and the transcript shows the stop.

## Surprises & Discoveries

- Observation: inside the adapter's `result` handler (dist/acp-agent.js, `case "result"` around lines 3395–3870) the order of emissions is: raw `_claude/sdkMessage` (line 2594, before the case dispatch), then the origin `usage_update` (line 3554), then, for human results only, result-time text (line 3785: local-only commands, and cache-replayed turns where `usage.output_tokens == 0` and nothing streamed), then the prompt reply. Autonomous results never emit text at result time (they leave at the early `break` near line 3618).
  Evidence: line numbers above; the trailing text path is guarded by `shouldForwardResult` at line 3775.
- Observation: a plan review answered with a cancelled outcome, which is how the worker hands an approved plan to a continuation prompt, makes the adapter throw "Tool use aborted" (`parseClaudePermissionSelection` in `dist/permissions/effects.js`). It is not a deny with `interrupt: true`, so the planning cycle can end with an ordinary success result rather than an interruption report. The coordinator cannot see the hand-off; only the prompt loop knows it is under way.
  Evidence: `dist/permissions/effects.js` lines 3-9; `mj-worker/src/acp/plan_tests.rs` answers the planning prompt with `end_turn`.
- Observation: besides the text at line 3785, the adapter sends result-time text in two more places the plan did not list: a refusal's explanation (near line 3700, `lastRefusalExplanation`), and the Markdown it builds for `/usage` (`takeUsageMarkdown`), which is not the result's text, so a prefix match against the result text would not recognize it.
  Evidence: `dist/acp-agent.js` near lines 3696-3706 and 3781-3790.
- Observation: the adapter fails a prompt at once for an error result (`failActive`), and it never holds the reply of a cycle that produced no model output, because such a cycle cannot have started background work.
  Evidence: `failActive` near line 2343; `turnAwaitingSubagents` near line 2245 holds only for subagents the turn spawned.
- Observation: Stop was not blocked by the worker for current clients. The chat and the phone send `CancelTurn`, which the relay already admitted and dispatched during a harness turn, and the ACP loop already answered a cancel outside a prompt with `session/cancel`. What blocked Stop was the clients' own gating: the chat's Esc acted only with a prompt in flight, and the phone offered interrupt only with an active prompt. The relay refused only the older `Cancel` command.
  Evidence: `mj-chat/src/chat/keys.rs` (Esc handler), `mj-chat/src/chat/active/dispatch.rs` (`cancel_agent`), `mj-controller/src/server_runtime/snapshot.rs` (`interrupt_turn`), `mj-worker/src/relay/commands.rs` (`queued_controls_before` admits `CancelTurn` while `running_turn`).

## Decision Log

- Decision: the completion decision moves from the ACP loop (`mj-worker/src/acp/session.rs`) to the relay coordinator (`mj-worker/src/worker_runtime/unix/dispatch.rs`). The drive layer forwards `RuntimeEvent::ClaudeTurnResult` on the same ordered runtime-event stream as `RuntimeEvent::SessionUpdate`. The coordinator records the completion and asks the loop to release the prompt future; the loop no longer emits `PromptFinished` for a result-driven completion.
  Rationale: only the runtime-event stream preserves the adapter's notification order. With the decision in the loop on a side channel, streamed text and the completion could be recorded in either order. With the decision in the coordinator, everything the adapter sent before the result is recorded before the completion, and everything after it (the marker, trailing text) is recorded after it, deterministically. Part one's plan said "do not route through the coordinator" because the loop must leave the prompt arm before the next queued prompt is dispatched; that is solved by sending the release request on the same command channel, ahead of the promotion.
  Date/Author: 2026-09-23, Fable.
- Decision: an "interruption report" never ends a prompt, regardless of steer or plan state. An interruption report is a human-origin result with `is_error` true whose diagnostic (the `result` string on success results, or the `errors` entry starting with `[ede_diagnostic]` on error results) starts with `[ede_diagnostic]` and contains the token `result_type=user`. This replaces part one's Milestone 3 injection bookkeeping.
  Rationale: the adapter itself identifies the steer abort and the plan-mode interruption by exactly this shape (`isEmptyUserInterruptionDiagnostic` at the top of dist/acp-agent.js and the `result_type=user … stop_reason=tool_use` test near line 3672). Claude Code produces this shape only for cycles it interrupted, so it is safe to ignore always, and no injection state is needed.
  Date/Author: 2026-09-23, Fable.
- Decision: text that the adapter forwards at result time is attributed to the turn that just ended, not to a new harness turn. The relay remembers, from a result-driven completion, whether trailing text is expected (`local_command` present, or `usage.output_tokens == 0`) and the result's text; agent text chunks that follow and are, concatenated, a prefix of that text are recorded as ordinary session updates of the finished turn. Any other agent output clears the expectation and behaves as before.
  Rationale: without this, the trailing text of a `/context`-style command or a cache-replayed answer would open a harness turn that nothing settles.
  Date/Author: 2026-09-23, Fable.
- Decision: for Claude, a harness turn settles on any SDK result that does not end an active prompt; the origin `usage_update` marker is no longer a settle signal for Claude. Codex is unchanged.
  Rationale: one boundary signal per harness. The marker is omitted when `lastAssistantTotalUsage` is null, which is the cause of the stray-chunk limitation.
  Date/Author: 2026-09-23, Fable.
- Decision: Stop during a Claude harness turn is admitted and sends `session/cancel`. The cancel command completes when the harness turn settles on the interrupted cycle's result. Stop with no turn open at all stays rejected.
  Rationale: the adapter's `cancel()` interrupts a live cycle (and settles a held prompt as cancelled, which the detached reply task discards). Refusing Stop was a workaround for not knowing when such a cycle ends; part one and Milestone B remove that reason.
  Date/Author: 2026-09-23, Fable (user requested both follow-ups).
- Decision: (revises the first decision above) the coordinator does not record the completion itself. On a result that would end the running prompt it sends `CommandRequest::ReleasePrompt { request_id, received, stop_reason, usage }` to the prompt loop, and the loop decides: it ends the prompt unless a cancel is in flight, an approved plan is being handed to its continuation prompt, or the result arrived before the current `session/prompt` was sent. When it ends the prompt, the loop settles a pending steer, emits `PromptFinished` with the result's stop reason and usage, detaches the reply future into a task owned by the connection, and leaves the prompt arm. The coordinator therefore needs no cancel tracking, no in-flight guard on `PromptFinished`, and no knowledge of the plan hand-off.
  Rationale: only the loop knows the three states that make a result not the end of a prompt. The plan hand-off is the case that forced this: its planning cycle can end with an ordinary result (see Surprises), and the hand-off then sends a second `session/prompt` under the same request id. The ordering property the first decision wanted still holds: the result reaches the coordinator after everything the adapter sent before it, and the loop emits `PromptFinished` only after the coordinator's request, so the answer is always recorded inside the prompt's turn. A prompt still completes exactly once, because every path in the loop that emits `PromptFinished` leaves the prompt arm at once, and a release for a prompt that already ended is ignored.
  Date/Author: 2026-09-23, Opus (implementation), after reading the adapter source.
- Decision: each result carries its arrival position on the ACP connection (`ClaudeTurnResult::received`, stamped in `drive.rs`), and the loop records the count just before it sends each `session/prompt`. A release whose result arrived at or before that count is ignored.
  Rationale: the plan hand-off reuses the prompt's request id, so a planning result that the coordinator relays late must not end the implementation prompt. The same check stops any result that arrived before a prompt from ending it.
  Date/Author: 2026-09-23, Opus (implementation), after reading the adapter source.
- Decision: (replaces the trailing-text expectation above) there is no relay expectation for trailing text. Instead, a successful result whose cycle produced no model output (`num_turns == 0`, or `usage.output_tokens == 0`), a failure (`is_error`, except a refusal or `max_tokens`), and a sign-in failure do not end the prompt; the adapter's reply does, as before this work.
  Rationale: the adapter sends result-time text only for such cycles, and it never holds their reply, so the reply still ends the prompt at once, and it arrives after the text on the same stream. The text therefore lands in the prompt's turn with no relay state, including the `/usage` Markdown that a prefix match would have missed. For failures, the adapter fails the prompt at once, and its error carries what the worker's failure handling uses: the "prompt failed" warning, which credential recovery matches, the auth-required marker, and the ACP error code. The remaining gap is a refusal's explanation text, which can arrive after the completion and open a harness turn; Milestone B settles that turn at the next result.
  Date/Author: 2026-09-23, Opus (implementation), after reading the adapter source.
- Decision: a human result with `queued_turn_count` above zero does not end the prompt.
  Rationale: Claude Code says another user cycle follows, which is how a steer's interrupted cycle ends when the steered message is still queued. This, the interruption-report rule, and the failure rule together cover steering without injection state.
  Date/Author: 2026-09-23, Opus (implementation), after reading the adapter source.
- Decision: (revises the Stop decision above) a Stop during a Claude harness turn completes when `session/cancel` is sent, as a prompt's cancel does, and the harness turn ends separately when the interrupted cycle's result arrives. No snapshot field for a cancelling harness turn is added.
  Rationale: this is how a prompt's cancel already works (`CancelApplied` completes the command; the prompt ends at its reply), so clients and the snapshot need nothing new, and there is no stored state to make compatible. The checkpoint barrier keeps waiting for the turn until the cycle has actually stopped, which settling the turn at the cancel would not guarantee. A harness turn opened by output that belongs to no cycle is not ended by Stop; the next result ends it (Known limitations in the design note).
  Date/Author: 2026-09-23, Opus (implementation).
- Decision: the chat and the phone treat a harness turn as stoppable when no goal is active (`SessionActivity::harness_turn_started_at_ms` with `!pursuing_goal` in the chat, `harness_turn` with `!goal.active()` on the phone).
  Rationale: clients do not know the relay's harness-turn policy. A Codex harness turn is always a running native goal, which has its own controls; a Claude harness turn is not.
  Date/Author: 2026-09-23, Opus (implementation).

Harness turns: `DurableRelay::record_session_update` (`mj-worker/src/relay.rs:836-919`) opens one when agent output arrives with no active prompt (`opens_harness_turn`, line 932) and settles it when a `usage_update` carries `_meta["_claude/origin"]` (`claude_turn_origin` in `mj-worker/src/relay/background.rs:21-40`) and `snapshot.harness_turn.is_some()`. Stop: the user's Stop becomes `RelayCommand::Cancel`. `mj-worker/src/relay/commands.rs:349-374` rejects it when no prompt is active but a harness turn is open, with the message about the agent working on its own. The adapter's `cancel()` (dist/acp-agent.js around line 4635) interrupts the live SDK cycle and settles a held turn as cancelled.

## Plan of Work

Milestone A revises part one's Milestone 2 and 3. If part one has already been implemented with the decision in the loop, refactor to this shape; if not, implement this shape directly. In `mj-worker/src/acp/drive.rs`, the `_claude/sdkMessage` handler sends `RuntimeEvent::ClaudeTurnResult(result)` on the same sender it uses for `RuntimeEvent::SessionUpdate`, so results are ordered with updates. In `dispatch.rs`, handle `ClaudeTurnResult` like this. If the harness is Claude, a prompt command is in `in_flight`, the result answers a user prompt (origin absent or `human`), the result is not an interruption report, and no cancel is in flight for that prompt (track this in the coordinator when it dispatches `Cancel`; clear it when the prompt completes), then: send `CommandRequest::ReleasePrompt { request_id }` to the loop, remove the prompt from `in_flight`, and call `relay.record_command_completed(&request_id, RelayCommandOutcome::Prompt { stop_reason: result.relay_stop_reason(), usage, diagnostic })`. The release request must be sent before `record_command_completed`, because that call promotes the next queued prompt, and both travel on the same channel, so the loop leaves the prompt arm before it sees the next prompt. Otherwise, if a harness turn is open and the result does not answer an active prompt, settle it (Milestone B). Otherwise ignore the result (a placeholder with no turn open, an autonomous result during a prompt, an interruption report).

In `session.rs`, add `CommandRequest::ReleasePrompt { request_id }`. Inside the prompt loop, if it names the running prompt: settle a pending steer exactly as the reply arm does, hand the `prompt` future to a detached task that awaits and discards the reply (never emitting any event for that `request_id`), set `prompt_running = false`, and `break` without emitting `PromptFinished`. If it names a prompt that is not running (the reply won the race), ignore it. Outside the prompt loop, ignore it.

Make a second completion harmless in the coordinator, not in the relay: on `PromptFinished`, if the `request_id` is not in `in_flight`, log at debug level and do nothing; `record_command_completed` keeps its `require_in_flight` invariant.
