# Recalibrate needs-input (?) versus important (!) on live GLiDE turn verdicts

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. It follows `.agents/PLANS.md` in the repository root.


## Purpose / Big Picture

Mjolnir (`mj`) marks each top-level session in the TUI and web session lists with an attention glyph. `?` means the agent needs the person's input; it stays until the person answers or dismisses it. `!` means the agent delivered something the person should read, such as an answer they asked for; it clears when they view the session. `✓` means there is unread output that needs nothing. On 2026-11-16 the user reported that many informational turns show `?` when they should show `!`. A wrong `?` is costly: it is sticky, it sends a notification, and it trains the person to ignore real questions.

After this work, informational turns that the user's rules place under `!` show `!` instead of `?`, real questions still show `?` at no worse than the previous recall, and we have a measured estimate of how many real questions show no `?` at all (false negatives). The evidence comes from live production verdicts logged since GLiDE (the hosted classifier described below) replaced Jev on 2026-11-12, not from the older offline corpora, which no longer exist on this host.

## Context and Orientation

A turn is one agent response to a prompt. When a top-level session's turn completes, the worker (`mj-worker`, the per-session process that runs the agent harness) sends the turn's evidence to a hosted classifier and turns the answer into an action. The classifier is GLiDE, a Fastino model reached through our proxy route `/v1/glide-turn-verdict`. GLiDE answers several multiple-choice questions at once and returns a probability for each option. The questions and their wording are in `mj-core/src/activity/eot_glide_questions.json`: `failure`, `input`, `work`, `background`, `turn_state`, `permission_veto` and `attention`. Managed sub-agents are not classified (`DurableRelay::classifies_turns` in `mj-worker/src/relay/verdict.rs`).

The rule that turns probabilities into an action is `action` in `mj-core/src/activity/eot_glide.rs`. Its constants are `REQUIRED_INPUT = 0.15844652713727195`, `DEMOTE_REQUIRED_CEILING = 0.5` and `IMPORTANT_ATTENTION = 0.488819272011068`. The action is `AwaitInput`, which shows `?`, when `input.required >= REQUIRED_INPUT` and the turn is not demoted. A turn is demoted when `input.required < 0.5` and `attention.important >= IMPORTANT_ATTENTION`. `AwaitInput` also results from `failure.other >= 0.90`. Otherwise, `glide_attention` in `mj-worker/src/relay/verdict.rs` marks the turn Important, which shows `!`, when `attention.important >= IMPORTANT_ATTENTION`. The daemon owns the session's attention state (`SessionAttention`). Two daemon rules change when a `?` appears or disappears without changing the turn's verdict. Hold: while the agent waits on managed children, native sub-agents or an imminent turn, `?` is held and shown when the wait ends. Latch: an open request stays `?` until the person answers or dismisses it, even across later agent-only turns. A latched `?` can therefore sit above an informational latest reply.

The shipped cuts were fitted on 2026-11-12 for about 90% needs-input recall at a 3% false-alert budget, on an offline census of 2,545 double-labeled turns. The user's labeling rules from then still apply and are restated here. Any question, choice, menu, offer that waits for yes or no, approval request, review request, missing fact or external action put to this person needs input, solicited or not (2026-11-06). A redundant request for permission to do work the person already assigned also counts as needing input while automatic continuation is off (2026-11-12). A reply that delivers an answer, recommendation, analysis or opinion that the person's latest message asked for is Important, even when it asks nothing back; a plain report of completed implementation work is not Important (2026-11-12). An unanswered request in any reply since the person's latest message still counts. A request made before that message is set aside unless a later reply restates it. Questions to other agents, rhetorical questions and questions the agent answers itself do not count.

The live evidence is in each worker's decision log: `~/.local/share/mjolnir/workers/<worker id>/jev-decisions/decisions.<n>.jsonl`. Each line is a JSON record. Records with `kind == "assessment"` describe one turn assessment. The same `id` can appear on several lines; the last line wins. Inside `technical.assessment` are `turn_id`, `completed_ordinal`, `completed_at_ms`, `evidence` (with `authorization.messages`, the chronological user and assistant messages GLiDE saw, plus runtime facts such as background commands), `glide` (the probabilities for each question), `action` and `status`. `technical.questions` holds the wording that was sent. Statuses include `superseded`, `assessed`, `consumed`, `pending` and `deferred`. Each worker keeps at most four rotated files of about 8 MiB, so busy sessions lose older records; coverage must be measured, not assumed. The daemon store at `~/.local/share/mjolnir/mj.sqlite3` holds session metadata and transcripts; read it only through read-only SQL (`file:...?mode=ro`), never from a test build.

The transcript text in this evidence is private. All corpus files, rendered items and labels stay under `/mnt/optane/tmp/attention-live-20261116/` on this host and never enter the repository or leave the host, except as GLiDE requests that the user has authorized. Only scripts and aggregate counts enter the repository.


## Plan of Work

Two terms are used throughout. An episode is the span from one genuine person message to the next in the same session; generated prompts such as mailbox wakes and sub-agent reports do not start episodes (`mj_core::continuation::GeneratedPrompt` defines them). An onset is the first turn in an episode whose verdict is `?`. Because of the latch, one onset can keep `?` displayed over many later turns, so the onset, not the turn, is the primary unit of analysis: it is the moment the person is interrupted. Turns are the secondary unit.

Milestone 1 builds the corpus. A standard-library Python script, `scripts/attention-live-corpus.py`, reads the decision logs copied into the study directory (`raw-decision-logs/`; rotation deletes the live copies), keeps assessment records that carry GLiDE probabilities, and keeps one record per turn (the latest non-superseded record for each session and `turn_id`). It recomputes the action and the attention with a Python port of `action` and `glide_attention` and compares the result with the logged action. Disagreements must be explained by a wording or rule version, identified by hashing `technical.questions` and by commit dates (`5eba12d1b` added the demote rule on 2026-11-12, `6dfb81125` removed continuation on 2026-11-13). Every candidate fix is applied to the logged probabilities, so older records are rescored with the current rule. The script excludes automated top-level sessions (evaluation and grading sessions, `jev-panel-work`, bifrost smoke runs) by session metadata from the store, before any sampling. For each turn it records the verdict glyph and the displayed glyph (after the latch and Hold rules in `mj-controller/src/daemon/attention.rs`), the person's next genuine message and the delay before it, and whether that message looks like an answer (it quotes the reply with `>`, or is a short yes, no, go-ahead or option choice). It also records whether the person dismissed the `?` instead of replying. A dismissal is a `RelayCommand::DismissQuestion` that the daemon submits to the worker with command ID `dismiss-question-<completed ordinal>` (`mj-controller/src/daemon/actions.rs`, the `NotificationDismissal::Question` arm), so it is in the worker's relay journal; the daemon also persists a read receipt with source `notification-dismissal`. The script must find where those are stored, copy the journals before they compact, and report from which date dismissals exist. A dismissal with no reply is a false-`?` candidate, not a label. The script then writes `episodes.jsonl` (onset, repeats of the `?` verdict, other turns under the latched `?`, how the `?` was cleared), `display-counts.md`, a coverage report against completed turns in the store, and `onsets-digest.md`: verbatim excerpts of 40 onsets drawn with a recorded seed, at most 3 per session, including every onset with `input.required` in [0.158, 0.5). The digest is built mechanically, so that it does not do the classification it is meant to inspect. For each onset it gives the last 600 characters of the person's latest message; from every reply since that message, each sentence that ends in a question mark or matches a fixed case-insensitive phrase list (should I, want me to, do you want, if you want, let me know, tell me if, your call, needs your, awaiting your, approve, confirm, go ahead), with its reply index and one sentence on each side; and always the last 600 characters of the final reply, with onsets that match nothing marked and kept.

Milestone 2 takes the policy questions to the user before any labeling, because the answers decide what to label and how much. The parent reads the digest and presents counts with verbatim examples (they are the user's own transcripts) for four questions. First, should a reply that answers the person's question and then proposes a next step ("Should I do X?") show `?` or `!`? Second, the same for an optional offer ("tell me if you want me to file an issue"). Third, should a latched `?` stay displayed over later informational turns, or should the display show the latest turn's state and keep the open question findable some other way? Fourth, what unit should the false-alert budget use: onsets, episodes or turns? The 3% per-turn budget from 2026-11-12 does not transfer, because one unanswered ask under the latch now counts once per later turn. Each answer is recorded in the Decision Log.

Milestone 3 freezes the study design and then labels. Before the first label, write `FREEZE.md` in the study directory and add the same content to this plan: the unit and the estimands (needs-input recall and false-alert rate in the user's chosen unit, `!` precision), the exclusion list, the labeling instructions and seeds, the candidate fix families and the selection rule, the pass rule and how a narrow miss is read, the current wording hash, and the freeze date. Labels are attributes, not one exclusive class, because one reply can both answer and offer. Each item records: whether it delivers an answer the person's latest message asked for; whether it is a completion report of assigned work; the ask type (none, blocking, proposal awaiting yes or no, optional offer, redundant permission); the index of the reply holding the ask; and the quoted ask. A blocking ask is a decision, approval, missing fact, review or external action the agent needs before it can continue. Labelers are subtle-type sub-agents. They see the chronological messages GLiDE saw, rendered as numbered replies. They never see probabilities, glyphs, the next message or the source population, and items are shuffled. About 20 seeded items whose ask sits in an early reply measure each labeler's hit rate on carried-over asks; `?` turns have a median of 11 replies since the person's message. The populations, sized to the user's Milestone 2 answers, start from: every onset, labeled twice blind with a third adjudicator on disagreement; repeats and turns under a latched `?`, labeled once (same ask still open, new ask, or none); a census of episodes that never show `?`, with the last turn of each labeled twice, because it carries every reply since the person's message; every turn with `input.required` in [0.05, 0.158) labeled twice, and 50 from [0.01, 0.05), with weights recorded; every turn shown `!` and every demoted turn, which is where a real ask would hide and which gives `!` precision; and the behavioral candidates (answer-shaped next messages after a non-`?` turn). The important-recall sample (turns shown neither `?` nor `!` whose latest person message was a question) waits until the user's answers show it matters. After labels are frozen, an audit pass shows an adjudicator the person's next message for every disagreement between label and behavior (an answer to a non-`?` turn, a dismissal of a `?` labeled blocking). Corrections are recorded beside the original label, never overwritten.

Milestone 4 scores fixes. Selection uses session-grouped cross-fit on all current data: about 40 sessions, too few for a held-out split to confirm 90% or 3%. ## Idempotence and Recovery

The corpus and scoring scripts only read the logs and the store, and they rewrite their output directory, so they can be rerun. Decision logs rotate, so rerunning later yields a different corpus. Never change `FREEZE.md`, the seeds or the item key after labeling starts; record any later change as a dated amendment in the Decision Log. A code change can be reverted by restoring the previous constants and wording.
