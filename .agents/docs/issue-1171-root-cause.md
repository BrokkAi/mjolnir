# Issue #1171: delayed delegation dispatch

Investigated 2026-09-27 against incident build
`389a166619e24aa561870bae00c2d2aa32b8e4b8` and checkout `abe49acb`.
Scope: diagnosis only; no runtime changes or live-session mutations. Follow-up
investigation used read-only SQLite access after the original daemon exited
and its log was removed by retention.

## Finding and confidence

The session-update coalescer has a reproducible starvation defect. It stores
updates in a `BTreeMap` keyed by session ID and always removes `pop_first()`.
A busy smaller-ID session can repeatedly reinsert itself ahead of an already
waiting larger-ID session. Replacing the larger session's payload does not
improve its position. There is no bound on how long it can be bypassed.

The first investigation established this defect with a synthetic stress test;
that alone was insufficient to attribute the incident to it. Its 100,000
dequeues were generated by the test, not observed in production.

The follow-up found a matching historical signature in durable API activity
records: for 226 seconds, 232 live-detail activity changes were recorded for
17 smaller-ID sessions and none for this parent or any larger-ID session.
The larger-ID sessions then reappeared in ascending ID order. Meanwhile, the
parent's transcript kept advancing in the local database. This strongly
supports starvation between materialization and server publication/dispatch,
rather than a parent-worker network stall. Exact enqueue/dequeue timing was
not logged, so the particular coalescer and the time spent in each stage
remain unmeasured.

The six-figure production count was warning amplification from repeated
full-state reads, not six-figure worker activity. Those unnecessary reads are
a separate confirmed implementation problem. Their precise contribution to
the service delay is not established by a historical CPU profile.

The unsupported-row count is a follow-up database observation. The aggregate
warning count divides exactly into 1,303 passes over that set; the original
log is no longer available to recount each individual row. API events are a
filtered durable interface, not a count of actor snapshots or relay deltas.
The coalescer's actual enqueue/dequeue counts were not recorded.

Confirmed repeated work in the incident source:

1. `daemon/process.rs::spawn_manager_target_refresher` runs a 500 ms timer
   and calls `Controller::load` unconditionally. Each load reads configuration,
   loads all session records and relationships, validates them, and checks
   runtime backfill. The timer is a source of repeated scans even without
   session changes; two loads per second is its configured cadence, not a
   guarantee when the load itself is slow.
2. `daemon/snapshot.rs::publish_session` publishes a daemon revision for each
   forwarded session view. `server_runtime/run.rs` reacts to those revisions
   by requesting another `Controller::load`. An in-flight reload coalesces
   requests, but sets a flag to run another load immediately afterward.
   Ordinary worker activity therefore invalidates the server's entire
   controller state rather than just the changed session.
3. `database/state_io.rs::load_state_from` warns for each unsupported row on
   every read. `database/session_move.rs::decode_move_operation` likewise
   repeats its warning whenever the same historical move is read. These
   diagnostics are generated by reads, not new failures or worker events.
4. Every worker update and daemon revision marks native-agent summaries dirty.
   `server_runtime/snapshot.rs::load_native_agents` iterates every loaded
   session, opening a separate SQLite reader for each. Completion publishes
   another viewer snapshot even if the resulting summaries are unchanged.
5. The server loop clones the conversation map and rebuilds the all-session
   viewer snapshot on updates. Preview generation walks and allocates the
   conversation's lines before keeping only the final four. The exact CPU
   cost during the incident is unmeasured, but the repeated work is explicit
   in the code and shares the loop that observes delegation requests.

These are multiple consumers rebuilding state the daemon already owns.
There is no evidence that the repeated warnings themselves are the sole or
dominant bottleneck. The logger sends them to a separate writer thread;
formatting/allocation and repeated reads still cost work.

## Code path

- `session_manager/standalone.rs::sync_in_place` polls durable subagent state
  and detects changes independently of the transcript.
- `session_manager/actor.rs::view_is_unchanged` compares subagent requests and
  results. Both checks were already present in the incident build.
- `session_manager/channels.rs::CoalescedUpdateSender::send` replaces the
  pending payload by session ID; `SessionManagerUpdates::pop_pending` removes
  the lexicographically smallest ID, irrespective of waiting time.
- This coalescer appears three times on the delegation observation path:
  actor to continuation service, continuation service to daemon process loop,
  and phone remote-session facade to server runtime.
- `daemon/process.rs` forwards the continuation service's updates through
  `RemoteSessionPublisher`; `session_manager/remote.rs` republishes those
  through the third coalescer.
- `server_runtime/run.rs` only calls `subagent_dispatch.observe` after
  receiving that last update. Independent dispatch jobs cannot help requests
  that have not reached this point.

The relevant coalescer, continuation, standalone polling, and dispatch files
have no differences between the incident commit and this checkout. The
follow-up also checked the daemon process, daemon snapshot, server loop,
viewer snapshot, and state-reader files against that commit.

## Reproduction and limits

An isolated Rust harness compiled with `rustc --edition=2024` uses the actual
repository bodies of `send` and `pop_pending`, with stub wake notifications
and upgrade guards. It queues the affected parent, then inserts a smaller-ID
update before each of 100,000 receives. Every receive selects the smaller
ID. Updating the parent's payload every tenth iteration does not help. The
parent is finally returned, with its latest payload, only after the smaller
publisher stops. Harness and binary are in
`/mnt/optane/mjolnir-1171-analysis/`. This proves the scheduling defect, not
the historical workload's exact timing; it is not a full daemon regression.

Intermittent network trouble could aggravate pressure on the update pipeline,
but no direct network stall is demonstrated here. Continued local transcript
replication during the publication gap argues against loss of contact with
this worker as the direct explanation. The warning storm in #1172 comes
from repeated reads as described above; its overhead remains unprofiled.

## Corrective direction

Remove the repeated work at its source. Have the daemon's existing owner
publish changes to records, targets, and configuration when those facts
change. Session activity must not trigger full-state reloads. Configuration
file changes need a separate change signal; unchanged configuration must not
reload historical sessions. Native-agent identity changes should invalidate
the affected owner's summaries only. Build previews from the needed tail
and avoid deep-copying every conversation for unrelated session updates.
Deduplicate diagnostics for unchanged historical records without deleting
those records or hiding new failures.

Preserve one latest payload per session while scheduling pending sessions
fairly. For example, a FIFO of distinct pending session IDs and their latest
payload map must share one owner/lock. Replacing a payload must retain the
session's existing queue position; publishing after delivery goes to the
tail. This removes the possibility of smaller IDs overtaking indefinitely.

Add a regression that keeps smaller-ID sessions active while asserting a
waiting parent's latest delegation state reaches dispatch within a bounded
number of dequeues. Cover all uses of the shared coalescer and retain
request identity/eventual completion after caller timeout. Add queue-age and
request-stage tracing to distinguish transport, publication, scheduling,
profile discovery, registration, and result delivery in future incidents.
Increasing the tool timeout does not repair starvation.

Delegation observation should belong to the worker control path, rather than
depending on the dashboard publication pipeline. Reducing repeated reads
alone would not remove the coalescer's structural starvation possibility;
changing the queue alone would leave the unnecessary whole-state work.
