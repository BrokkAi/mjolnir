# Terminal verification campaign for the changes of 2026-09-17 to 2026-09-19

This is an agent-facing runbook for exercising, in a real terminal under tmux, everything user-visible that landed in `mj`'s dashboard between 2026-09-17 and the close of the Live-tab ExecPlan (`.agents/plans/goto-live-sessions-tab.md`) on 2026-09-19. Unit and render tests cover most of it; this campaign is for what they cannot see — whether the thing actually works when a person presses the keys.

The campaign is local, disposable, and parallel. Five workers, each an Opus agent, own one track each, one isolated fake-ACP lab each, and one private tmux server each. A coordinator (Fable) prepares nothing on their behalf beyond this document, reads every finding, triages, and dispatches fixes as separate agents after the campaign. **Workers do not fix anything.** A worker that finds a bug records it and moves on; a finding is only useful when its exact keys and captures are saved so it can become a regression test.

## Terms

`mj` is the dashboard binary, built at `target/debug/mj` by `cargo build -p brokk-mjolnir -p brokk-mj-worker` from the repository root. The **prefix** is `ctrl+b`: press it, release, then a second key; `prefix+g` means `ctrl+b` then `g`. A **session** is one agent conversation; a **workspace** is a named group of sessions drawn as a tab across the top of the dashboard. The **fake ACP** is a scripted stand-in for a coding agent that the lab wires in as profile `fake` on target `localhost`; it answers every prompt with a canned reply after a fixed delay and never asks questions.

## Prepare (each worker does this once, for its own track)

Work from `/home/jonathan/Projects/hel4`. Every command here opens loopback or Unix sockets, so run outside any restricted sandbox with elevated permissions; an `EPERM` from a sandboxed command is not a product result.

The binary is shared and already built by the coordinator at the campaign commit; do not rebuild it, because a worker rebuilding mid-campaign changes what the other workers are testing. Record what you are testing:

    git rev-parse HEAD
    sha256sum target/debug/mj

Prepare your lab with your assigned seed and note the three lines it prints:

    python3 tests/e2e/prepare-luna-lab.py --seed <SEED> --hel ./target/debug/mj

It prints `artifacts=<dir>`, `runtime=<dir>`, and a `source <file>` line. The environment file exports `MJ_CONFIG_DIR` and `MJ_DATA_DIR` (a disposable config and state, so nothing you do touches personal Mjolnir state), `MJ_CHAOS_ISOLATED=1`, `MJ_LUNA_ARTIFACTS` (your lab's root, which is also where all your evidence goes), `MJ_LUNA_BINARY`, `MJ_LUNA_PORT`, and `MJ_LUNA_FAKE_ACP_DELAY_MS`. The fake ACP answers prompts after that delay, 15 seconds by default; that window is how you see a session in the *working* state, so keep the default.

Start a private tmux server named for your track, with a dashboard window sized 140×40 and a second window as your shell. The server name must be unique to you and must never be the user's own server:

    tmux -L mjv-<track> -f /dev/null new-session -d -s v -n mj -x 140 -y 40
    tmux -L mjv-<track> new-window -d -t v -n shell
    tmux -L mjv-<track> send-keys -t v:mj "source '<artifacts>/luna-env.sh'; exec \"\$MJ_LUNA_BINARY\"" Enter

Drive it only through `tmux -L mjv-<track> send-keys -t v:mj ...` and read it only through `tmux -L mjv-<track> capture-pane -t v:mj -p`. Two tmux facts matter. `send-keys` delivers keys to the pane directly, so `send-keys C-b g` reaches `mj` as the prefix chord even though tmux itself also uses `ctrl+b`; and because `mj` is running inside tmux with tmux's default prefix, the dashboard is entitled to show its inside-tmux collision notice on first launch — that is a Track A expectation, not a bug. Send text with `send-keys -l 'text'` and send Enter as a separate `send-keys Enter`. After any key that changes the screen, wait briefly (`sleep 0.3`) before capturing; after a prompt, wait for the fake delay.

The dashboard opens on an empty workspace. Create sessions through the New wizard: press `n` in the Sessions pane (or `prefix+c`), and expect **four** steps — profile (`fake`), target (`localhost`), local project directory, and a review — each accepted with Enter; capture each step, and read the target step before accepting it. The wizard never asks for a title, so name a session afterwards with `prefix+shift+t` (rename), because several missions select rows by title. The project-directory field remembers the last path between runs, so clear it before typing. To get a second workspace, use `prefix+shift+n` (the workspace manager) and create one; `prefix+n` and `prefix+p` move between workspace tabs, and `prefix+1`..`9` jump to one. Send a prompt by focusing the composer (`Tab` until the Prompt box has focus), typing text with `send-keys -l`, then Enter.

Timing and key delivery, learned the hard way: leave about half a second between `C-b` and the second key — at 0.2–0.3 s tmux dropped chords several times, which is harness timing, not a product bug. `send-keys ';'` never arrives, because tmux eats a bare semicolon; send `prefix+;` as `send-keys -H 3b`. `prefix+q` exits the process rather than detaching, so the window that `exec`ed the dashboard closes with it. Put any helper script you write under your own `$MJ_LUNA_ARTIFACTS/<track>/`, never in a shared scratch directory: in the first run two workers shared one `cap.sh` path and one overwrote the other's, misfiling two captures.

How to reach each session state the filters and badges use. *Working*: the 15 seconds after you send a prompt. *Done (unread)*: switch to another session or workspace before the reply lands, then let it land. *Idle*: open a done session and read it. *Blocked*: **not reachable in this lab.** The fake never asks a question, and killing the fake adapter, the adapter mid-turn, or the whole `worker run` process does not produce a failure either — the controller daemon restarts the worker and the warnings count as unread replies. The `b` letter, the failure ranking, and the failed-session attach guard therefore stay covered by unit tests only; record them as not exercised rather than reporting the restart as a defect.

## Evidence standard

Write everything beneath `$MJ_LUNA_ARTIFACTS/<track>/`. Keep a `notes.md` that records, per mission, the wall-clock time, every key sent as the exact `send-keys` argument, what you expected, what you saw, and the capture file name. Save captures with `capture-pane -p > $MJ_LUNA_ARTIFACTS/<track>/NNN-<label>.txt`, numbered in order. Capture before and after every assertion, not only on failure.

A **finding** is a numbered entry in `findings.md` with: a one-line title; the exact reproduction as a sequence of `send-keys` calls from a fresh dashboard; the capture that shows the wrong state and the capture just before it; what the correct behavior is and which commit or document promises it; and a severity — *blocks* (a person cannot complete the task), *wrong* (the task completes but the screen lies or a key does the wrong thing), or *rough* (works, but a label, hint, alignment, or timing is off). Record a finding before doing anything else, and do not attempt a fix or a workaround; if the dashboard is wedged, note it, restart it, and continue.

When a mission passes, say so in `notes.md` with the capture that proves it. "It seemed fine" is not a result. Finish `notes.md` with a table of missions and outcomes, and end the run with the cleanup below.

## Cleanup (every worker, at the end)

Exit the dashboard with `C-b` then `q` (it exits rather than detaches), then kill your private tmux server: `tmux -L mjv-<track> kill-server`. Finding the lab's processes needs care: the controller daemon runs as `/proc/self/exe daemon-run`, so an argument grep for the runtime path misses it — its PID is in `$MJ_DATA_DIR/daemon.json`, and the reliable test for any process is whether `/proc/<pid>/environ` contains your `MJ_DATA_DIR`. Kill the daemon **first**, then the workers; a worker killed while its daemon lives is restarted with a new PID and needs a second pass. Kill by exact PID only; never `pkill` by name, because other workers' labs, in-container workers, and your own shell match. Check again after a few seconds. Leave the artifact directory in place; the coordinator reads it. Do not delete anything under `target/reliability-artifacts/`.

## After the campaign (coordinator)

Read each track's `findings.md`. For each finding, decide whether it is a product defect, a test-lab limitation, or a runbook error, and record that verdict beside it. Group product defects by area, then dispatch one fix agent per group with the finding's exact reproduction, the requirement to write a failing test from that reproduction first, and the usual validation (`cargo test`, `cargo clippy --all-targets -- -D warnings`, dev profile, outside the sandbox). Run fix agents in isolated worktrees, one per group, and cherry-pick their commits back in order: several agents editing one checkout clobber each other's files and break each other's `cargo test` mid-edit. Re-run only the missions the fix touched, on a fresh lab, before declaring the campaign closed. Record the outcome and the artifact directories at the bottom of this document.
