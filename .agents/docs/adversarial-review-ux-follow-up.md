# Review UX follow-up, 2026-09-05

The user approved session-status and progress fixes, rejected changes to primary model selection, and requested safer handling of an extra Enter during review. Global configuration, severity calibration, and failure prevention were design questions; they are documented here without introducing per-session review settings or a new prompt protocol.

## Implemented behavior

The TUI now retains the daemon's complete review projection for all sessions, including sessions that are not selected. Session rows and the active conversation title show typed review activity. Removing a review restores the underlying primary activity. Plan-review second-opinion stop warnings remain separate from turn-review state. Role completion is displayed as `done`, including in the web review projection, so a successfully completed supervisor is not labeled clean when it reports findings.

Running review opens a compact, scrollable Overview with the current stage, role progress, and prompt/cancellation guidance. Tab reaches raw reviewer transcripts. An arriving verdict selects Verdict automatically. Running action selection is explicitly absent; repeated Enter is harmless. Escape, a Cancel click, or deliberate action selection still cancels. Findings default to Forward and failed verdicts default to Dismiss. Coalesced snapshots that replace a previous verdict with a new review reset to Overview and clear action selection.

The cancellation audit also produced one narrow worker fix. `ReviewerRole::pause` now retains its runtime handle while awaiting active-prompt cancellation, then takes it for teardown. Previously the wait saw the removed handle and returned immediately. A scripted active-turn behavior test verifies exactly one cancel reaches the harness, completes durably, and is not replayed on compatible restart.

Validation completed with `cargo test` (2,271 passed, 0 failed, 12 ignored), `cargo clippy --all-targets -- -D warnings`, formatting checks, and `git diff --check`. Terminal behavior was exercised through the real render/key handlers with a test terminal, and worker cancellation through the scripted ACP harness. Logs are local under `target/adversarial-live/ux-*`; no new paid-model container session was created for this follow-up.

## Global configuration entry point

Add a `Review settings…` command to the existing F2 command palette under `Scope::Global`, available regardless of which session or pane is selected. It should open an in-TUI dialog editing only the shared `[review]` fields: automatic review, tier, profile, model, and effort. The existing `Open setup` action is a first-run stdio workflow, available only when configuration is absent; reusing it would be the wrong interaction and would suspend the dashboard.

Keep `HelConfig.review` as the one source of configuration. Save by loading the latest configuration in a supervised background operation, changing only its review section, validating, and using the existing atomic save mechanism. This avoids overwriting unrelated edits from a stale dashboard snapshot. The daemon already reloads review configuration through its target refresher and reads it at review admission; no per-session preference or second configuration file is needed. The settings dialog should state that changes apply to subsequent reviews. Effective reviewer identity/model/effort should remain inspectable for an in-flight review.

Advertised selector choices are runtime capabilities, not static lists to embed in the UI. Load them asynchronously from the selected profile's actual adapter environment, apply a candidate model before asking for its available efforts, and retain an explicit unknown/loading/verified state. A single global choice can still be incompatible with one target's older adapter; readiness belongs to a profile and execution environment even though preferences are global. Failed discovery must not silently choose a different model or write placeholder defaults.

Source anchors: `mj-tui/src/actions.rs` (`CommandSpec`, `Scope::Global`, `OpenConfig`), `mj-cli/src/dashboard/actions.rs` (`OpenConfig` handling), `src/hel_config.rs` (`ReviewConfig`, `HelConfig::save_to`), `mj-cli/src/daemon.rs` (review config watcher), and `mj-controller/src/hel_review_host.rs` (`begin`, `ReviewerIdentity`).

## Stable severity guidance

Keep severity judgment semantic and shared. `src/hel_review/lanes.rs` already centralizes `QUALIFICATION_GATES` and `PRIORITY_FINDING_CONTRACT`; extend one common policy rather than adding slightly different instructions to each prompt. Retain the existing `[P0]`–`[P3]` markers and clean sentinels, so calibration does not change output parsing or control flow.

The policy should order findings by demonstrated impact and reach, reserving P0 for unconditional catastrophic/release-blocking failures and making ordinary actionable defects P2 unless evidence supports greater urgency. Severity and confidence are separate: high confidence that a defect exists does not make it P0. Existing qualification gates still decide whether an observation belongs in the review at all, so a lower priority does not invite style noise.

Make the validator or extended supervisor responsible for final priorities and consolidating reports that describe one root cause and one corrective action. A failing regression test normally supports the code defect it exposes; it should not become a second finding. Different callers affected by one bug may be evidence of broader impact. Similar symptoms with independent causes must remain separate. Do not deduplicate with title equality, line-number rules, or a similarity threshold: those would make correctness depend on incidental wording.

Remove P0 as the only demonstrated example in prompt output forms; use an ordinary P2 example while listing the allowed markers separately. Add a short evidence rule distinguishing current code/test state from earlier primary reports, especially if the worktree changed after the reported run. Avoid example-specific instructions about Python ranges or equal bounds.

Validate calibration with a small behavioral evaluation set, not tests asserting paragraph wording: an ordinary boundary defect, an urgent broad-impact failure, an unsupported severe allegation, a defect plus its failing-test symptom, two distinct defects with similar symptoms, a stale test report after an external edit, and an intentional behavior change. Evaluate supported findings, duplicate root causes, justified urgency, and false-clean results; do not require identical prose or one exact priority on every ambiguous case. No new schema, severity parser, retry-on-wording rule, or fixture-specific prompt patch is required.

## Prevention before recovery

The previous live run showed a deterministic staging/conversation ownership bug, not random model unreliability. Separate staging snapshots, private role homes, and fresh generation identities were the appropriate repair. Configuration mistakes remain discoverable too late: static validation only checks profile assignment, while actual adapter selector validation happens during live startup. A background readiness check at settings save and after relevant environment changes can prevent repeating known-invalid starts; it must use the same underlying selector logic as real review.

Readiness should cover the selected model/effort and required review tooling on the actual target. Do not silently weaken review when required tools are unavailable, switch reviewer models, or apply blanket automatic retries. Retry a transient transport operation only when its outcome can be reconciled or it has an idempotent command identity. Preserve a visible unreviewed result when a review cannot complete. Fault-injection behavior tests for lifecycle transitions are more valuable than adding more instructions telling a model to recover from infrastructure failures.

The follow-up reliability audit and any verified additional defects are recorded in the execution plan. Claims about low failure rates require repeated measured runs; this work does not infer a reliability percentage from the small live fixture.

One concrete remaining hardening boundary is delivery of forwarded findings. `TurnReviewDriver::forward` emits `PromptPrimary` together with prior-review persistence, baseline advancement, and closure. `HostState::prompt_primary` spawns submission and logs an error without feeding acceptance or failure back into the review state machine. Consequently a rejected or unreachable primary can leave the user with a sent notice even though no corrective turn was accepted. The repair should make delivery an acknowledged transition: retain the findings until the primary accepts the command, then advance and close; on rejection retain an actionable failed handoff. Use the existing command identity to reconcile ambiguous transport outcomes rather than blindly issuing a second corrective prompt. The review's prompt hold must admit that internal handoff without opening a race for unrelated prompts. This requires a focused controller/actor lifecycle change and fault-injection tests, and is deliberately not represented as a UI fix.
